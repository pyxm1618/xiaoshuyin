# 3. IA Principles

## 3.1 Same truth, different projection

核心原则：

> **Same truth, different projection — never duplicate authority.**

同一个业务事实可以在首页、进展、我的或孩子受限入口中以不同信息密度展示，但不能形成第二份可独立修改、独立判断或独立推进的 truth。

## 3.2 Journey Chapter 只是叙事层

继承 Step 1 的五个 Journey Chapter：

1. 先弄清楚发生了什么
2. 决定这次先改变什么
3. 一起尝试办法
4. 看看真实发生了什么
5. 一起决定下一步

它们用于帮助用户理解当前旅程，不替代：

- Case Phase；
- Service State；
- stream position；
- Authorization；
- Consent；
- Safety；
- Review State；
- Validity State。

## 3.3 Current Focus 只是 Presentation Priority

Current Focus 回答：

> **现在最值得用户关注或完成的是什么？**

正式采用：

> **1 + N**

即：

- 首页视觉上突出 1 个主要 Current Focus；
- 业务上保留 N 个仍然合法的并行事项；
- Current Focus 不获得 Domain Authority；
- 主焦点变化不能取消其它合法 stream、re-entry、help、schedule 或独立 Review。

## 3.4 Presentation Mode 只有四种

只允许：

- Normal
- Reduced
- Serious
- Safety Priority

它们控制体验表达强度，不是 runtime state。

## 3.5 Client Authority Boundary

Frontend 不得自行计算或推断：

- Authorization；
- Consent；
- Safety；
- Case Phase；
- Case Status / Service State；
- Goal 是否正式成立；
- Plan / Plan Version 是否有效；
- `NEEDS_REVIEW`；
- stream eligibility；
- Review result；
- Closure；
- Professional Approval；
- viewer visibility。

业务合法性来自 server / Domain Authority。

Current Focus 的边界为：

- server/business layer 决定候选事项的业务合法性、blocking、required priority、viewer visibility、stream availability；
- frontend 决定在合法信息集合中如何组织、排序、渐进披露和视觉突出。

当前 main 没有冻结一个独立的 Frontend Viewer Projection endpoint / DTO；Step 2 不因此阻塞，也不自行设计该 API。

# 4. Viewer Model

V1 至少区分两类前端 viewer。

## 4.1 Parent / Guardian

Parent / Guardian 是 V1 主用户体验。

其主要职责包括：

- 建立/管理最小 Family / Person context；
- 查看当前主要 Case；
- 完成 Assessment / Formulation / Goal / Plan；
- 执行家长行动；
- 管理两条 Digital Use stream；
- 记录反馈；
- 查看 Review / Maintenance / Closure；
- 管理提醒、资料权利和历史 Case。

## 4.2 Invited Child

Invited Child 是：

> **Case-specific limited participant**

不是：

- 缩小版家长端；
- 默认 Family Manager；
- 自动拥有 Family membership management；
- 自动拥有 Common Core Goal / Plan authority；
- 自动拥有整个 Case 的 visibility。

实际可见内容必须是 viewer-scoped projection，并服从：

- Visibility；
- Purpose；
- Consent；
- Authorization；
- Case Participation；
- Data Rights。

Family membership、guardian relationship、identity binding、Case participation 必须保持不同概念，不能在 UI 中合并成一个“家庭成员权限”。

# 7. Home / Now

## 7.1 首页不是 Dashboard

首页只回答：

> **我现在最需要知道或做什么？**

首页不承担完整 Case 后台对象浏览。

## 7.2 首页结构

首页至少允许以下信息层级：

1. 当前主要 Case 的简短上下文；
2. 1 个主要 Current Focus；
3. 必要的 blocking / serious / safety information；
4. 少量仍合法的 secondary entry；
5. 通往完整“进展”的明确入口。

## 7.3 Current Focus 不创造业务资格

首页不得因为某事项未被选为主焦点而隐藏其业务存在。

例如：

```yaml
Primary Focus:
  Family Alliance feedback

Still Legal:
  - Phone Use Contract preparation
  - upcoming Review
  - Help
```

这仍然是合法的 `1 + N`。

## 7.4 高优先级业务抢占

当 server/domain truth 表明存在：

- Safety；
- required Consent；
- Plan invalid / NEEDS_REVIEW；
- blocking condition；
- required Review；
- Referral；
- WAIT / PAUSE；

首页应降低或替换普通 Current Focus。

抢占原因来自业务层；frontend 只呈现。

# 8. Progress / Journey

“进展”承担当前 Case 的完整 `1 + N` 阅读与进入能力。

它不是数据库状态列表，而是用户可理解的持续问题解决旅程。

至少必须保留：

- 当前 Problem Formulation；
- Current Goal；
- Current Plan / Plan Version；
- FAMILY_ALLIANCE；
- PHONE_USE_CONTRACT；
- 日程与安排；
- persistent Artifacts；
- Feedback；
- A5001 Review；
- A5002 Review；
- 历程记录；
- Help / support / re-entry。

## 8.1 进展中的 Journey Chapter

五个 Journey Chapter 可作为叙事分组帮助理解，但不能决定业务推进。

同一 Journey Chapter 内可以同时存在两个不同 stream position。

## 8.2 Problem Formulation

必须保留正式能力：

> 查看 → 纠正 / 补充 / 不同意 → 确认

不能因为“进展”视觉聚合而跳过确认或隐藏重新判断。

## 8.3 Goal

Current Goal 必须展示其当前正式状态。

current main 中：

- Goal SAVE 形成 immutable version；
- 正式 CONFIRM 针对 exact Goal/version；
- `ConfirmGoal` 是 Common Core `GOALS → PLANNING` 的唯一正式 owner；
- A2010 completion 只是其 prerequisite。

因此：

> A2010 不是“Goal confirmed”的 UI 同义词。

孩子对 Goal 的意见也不是 Common Core ConfirmGoal。

## 8.4 Plan

进展页展示 Current Plan / Plan Version，而不是复制一套“前端行动计划”。

Plan 必须保留：

- rationale；
- tasks；
- follow-up；
- review conditions；
- adjust / pause / safety conditions；
- current version / review state。

历史 Plan Version 保留为历史，不得静默覆盖 Current Plan。

## 8.5 Case Participation / Invitation

具备当前 Case management / viewer authority 的 Parent / Guardian，必须在：

> **进展 → Case Participation**

看到 server-authoritative participation projection，而不是把孩子参与混入 Family membership management。

该 projection 至少能表达当前 Case 下、当前 viewer 被授权看到的：

- PENDING；
- ACTIVE；
- DECLINED；
- EXPIRED；
- WITHDRAWN。

显示的状态、viewer visibility 与合法 next action 全部来自 server/domain authority。Parent / Guardian 可以消费真实 participation truth，但不能：

- 代替 Child 执行 Accept；
- 伪造 Child confirmation；
- 把 invitation / participation 当成 Family membership；
- 将 DECLINED / EXPIRED / WITHDRAWN 静默恢复为 ACTIVE；
- 因 binding attempt 失败自行改写 participation lifecycle。

只有当 server-authoritative projection 提供新的 invitation action 时，IA 才显示该 action；不得从 terminal state 自行推导“重新激活”。

# 14. Child Limited Participation IA

## 14.1 Child Participation Entry

孩子通过正式 Case Participation invitation 进入：

> **Child Participation Entry**

这是 Case-specific invitation landing，不是普通 Parent Case，也不是“加入家庭”。

在 server-authoritative viewer projection 允许的范围内，该入口只展示最低必要上下文，使受邀孩子能够理解：

- 自己收到一个 participation invitation；
- 谁是当前可合法展示的邀请来源；
- 这是哪个 Case / 当前允许展示的最小 Case context；
- 本次 participation 的有限范围；
- 当前可执行的合法选择。

未完成合法 identity binding 前，candidate 不得因持有 invitation 而获得 Family / Case restricted facts。邀请、Family membership、guardian relationship、Consent、identity binding、Case participation 始终是不同事实。

## 14.2 Authority lifecycle / flow outcome / IA surface

当前正式 participation lifecycle 只允许：

~~~text
PENDING
  → ACTIVE      (target explicit accept before expiry)
  → DECLINED    (target explicit decline before expiry)
  → EXPIRED     (server-authoritative expiry)
ACTIVE
  → WITHDRAWN   (active participant explicit withdraw)
~~~

Step 2 不创建其它 invitation / participation state。

| Category | Authority truth | Step 2 IA landing | 边界 |
|---|---|---|---|
| Invitation / pending participation-resource state | PENDING | Child Participation Entry → Identity Bootstrap（如需要）→ Participation Decision | PENDING 不等于 active Participant |
| Active participation state | ACTIVE | Case-specific Limited Participation Surface | 只获得明确授权的 limited capability |
| Pre-accept terminal participation-resource state | DECLINED | Declined terminal landing | 不自动关闭 Case，不产生 active participation |
| Pre-accept terminal participation-resource state | EXPIRED | Expired terminal landing | 当前 invitation 不能继续；next action 只服从 server authority |
| Post-accept terminal participation state | WITHDRAWN | Withdrawn terminal landing | participant capability 停止；历史保留 |
| Identity-binding attempt outcome | PENDING / COMMITTED / TERMINAL ATTEMPT REJECTION / RETRYABLE OPERATION FAILURE | Invitation-aware Identity Bootstrap | 不是 invitation lifecycle state |
| Flow / authorization failure outcome | unauthorized / no permission | Unauthorized / No Permission surface | 不改变 invitation state，不泄露 restricted facts |
| Identity flow failure outcome | wrong account / identity conflict / multi-family block / binding failure | Binding Failure / Identity Conflict IA landing | candidate-facing 必须遵守 anti-enumeration；不得 fake success |
| Identity flow waiting outcome | binding PENDING / second-party confirmation required | candidate：generic Binding Not Completed；authorized confirmer：minimum necessary pending task | 不是 invitation state，不得形成信息 oracle |
| Post-binding participation-decision state | binding COMMITTED + participation仍为 PENDING | Participation Decision | Binding Success ≠ Participation Active |

CANCELLED、REVOKED、FAILED、UNAUTHORIZED、BINDING_FAILED 均不得被 Step 2 写成新的 invitation terminal state。

## 14.3 Invitation-aware Identity Bootstrap

如果 target Person 已有正确 Account：

- 当前 authenticated Account 正确 → 复用 existing Account↔Person binding；
- 然后进入本次 Participation Decision；
- 不重复创建 Person，不重新做 identity bootstrap。

如果 target Person 尚无 Account：

> **必须进入 Invitation-aware Identity Bootstrap Flow。**

该 IA Flow 负责承接 current Authority 已存在的真实状态：

~~~text
Invitation Entry
→ Invitation-aware Identity Bootstrap
   ├─ candidate authentication / identity bootstrap
   ├─ binding pending
   ├─ required second-party confirmation / candidate recognition
   ├─ binding success
   ├─ identity conflict / wrong actor / unauthorized candidate
   └─ retryable or terminal binding failure
~~~

这里必须保持：

> **Account↔Person binding ≠ participation acceptance。**

binding 成功只建立身份关联，不自动产生 ACTIVE participation。

在 candidate 尚未成功绑定为 target Person 前：

- 不能展示受保护的 target Person / Family / Case facts；
- 内部真实原因可以由 server 保留；
- candidate-facing surface 必须遵守 current anti-enumeration authority，不能用不同错误文案或不同“下一步”泄露 guardian、consent、年龄、多 Family、其它 Account binding 等受限事实。

## 14.4 Binding Pending / Second-party Confirmation / Participation Decision

current Authority 仍存在真实的 identity-binding candidate confirmation + independent second-party confirmation。

因此 Step 2 必须承接 binding attempt 的真实 PENDING，但在 candidate 尚未成功绑定前：

> **不得把内部 PENDING_SECOND_CONFIRMATION / identity conflict 等原因直接暴露成可区分的 candidate-facing 状态。**

candidate-facing IA 只进入不泄露原因的 Binding Not Completed landing；已授权 confirmer / manager 只在自己的授权上下文看到完成确认所必需的最小 pending task。

只有完成 current Authority 要求的 binding gates 后，才可得到 binding COMMITTED。即使 binding 已 COMMITTED：

> **Binding Success ≠ Participation Active。**

系统仍进入本次 Participation Decision；只有 target Person 本人执行正式 Accept，才发生：

~~~text
PENDING → ACTIVE
~~~

因此 binding success 到 participation Accept 之间是真实的中间 IA 状态，不得被前端跳过或 fake success。

## 14.5 Participation Decision — Accept / Decline

完成合法身份条件后，孩子进入：

> **Participation Decision**

### Accept

target Person 本人显式 Accept：

~~~text
PENDING → ACTIVE
~~~

然后进入：

> **Case-specific Limited Participation Surface**

而不是 Parent Case 的完整 projection。

### Decline

target Person 本人可以明确 Decline：

~~~text
PENDING → DECLINED
~~~

DECLINED surface 必须：

- 明确显示本次 participation 已拒绝；
- 不再进入 ACTIVE limited participation；
- 不继续展示超出当前 server-authorized terminal projection 的 Case 内容；
- 返回 Child Participation Entry 的 terminal landing / 非 Case navigation；
- 仅显示 server-authorized next action。

Parent / Guardian 侧只消费 server truth；不能代替孩子 Decline，也不能把 DECLINED 当成失败、Case closure 或“不配合”。

## 14.6 ACTIVE Limited Participation / Withdraw

ACTIVE participant 进入：

> **Case-specific Limited Participation Surface**

在业务 Authority 允许时，孩子可以：

- 查看与本人相关且可见的信息；
- 对本人相关 Goal / Task 表达意见；
- 同意或拒绝本人需要参与的事项；
- 提交本人反馈；
- 完成本人明确被授权的 participation action；
