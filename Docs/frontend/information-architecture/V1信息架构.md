> 文档阶段：Step 2 — Information Architecture  
> 当前状态：In Progress — Entry Baseline Frozen  
> 上游体验基线：`Docs/frontend/experience/V1前端体验原则.md`

---

## 0. Step 2 目标

Step 1 已冻结“用户应该怎样感知小树荫”。

Step 2 负责把这套体验原则落成可验证的信息架构，但不能重新设计业务流程。

因此 Step 2 的正确顺序是：

1. 建立 **Experience ↔ Domain Traceability Matrix**；
2. 明确 Current Focus / Journey Trace 的 Authority 与投影方式；
3. 冻结 Step 2 的 Signature Experience Moments；
4. 再设计页面、导航、入口、层级和不同状态下的可达性；
5. 最后逐项反查 U01–U20、Case lifecycle、Service Status、Digital Use canonical nodes 与并行关系，证明没有业务能力因 UI 简化而消失。

本文件当前先冻结 1–3；**尚不冻结最终 Tab 名、页面数量、首页卡片结构或“进展”等具体命名。**

---

# 1. Step 2 不允许重新打开的 Step 1 结论

以下均直接继承 Step 1，不重新讨论：

- Current Focus ≠ 每日任务；
- 不使用“第 N 天”、连续签到或欠账式恢复；
- 首页/主入口不天然等于最高游戏化强度，Presentation Mode 与 Safety Priority 优先；
- 不能预设“问题一定在孩子身上”；
- “进展”不是已冻结 Tab 名；
- 体验单焦点，业务可多线程；
- Journey Chapter 不是第二套 Case Phase；
- 用户理解可以聚合，正式确认/授权/Review/并行流不能被业务合并；
- A5001 / A5002 必须保持独立；
- WAIT / PAUSE / UNKNOWN / WORSENED / Safety / Referral 必须保持真实语义；
- Maintenance、Closure、Relapse / New Round 不能被“通关”模型吞掉。

# 2. 前后端同一流程：Traceability 规则

这张对照不是新的状态机。

映射允许：

- one-to-many；
- many-to-one；
- parallel；
- cross-cutting；
- override。

禁止把复杂业务硬压成“一章 = 一个 Phase”。

---

## 2.1 Case Phase ↔ Journey Chapter

| 正式 Case Phase | 用户理解层 | IA 必须保留的事实 |
|---|---|---|
| INTAKE | Pre-Case / Chapter 1 入口 | 服务范围、登录、必要授权、当前问题入口不能被主 Case UI 吞掉 |
| ASSESSMENT | Chapter 1「先弄清楚发生了什么」 | 证据不足、来源冲突、分流、补充信息均是正常状态 |
| PROBLEM_FORMULATION | Chapter 1 | 必须查看、纠正、确认 PF；不能从 Assessment 直接跳方案 |
| GOALS | Chapter 2「决定这次先改变什么」 | Goal 确认与 A2003–A2010 的合法 forward flow 可同时存在 |
| PLANNING | Chapter 3「一起尝试办法」 | Plan Version、Intervention rationale、双 stream 不能被压成单一任务表 |
| EXECUTION | Chapter 3 + Chapter 4 | 现实行动、Feedback、障碍支持并存；部分执行/未执行不是失败 |
| REVIEW | Chapter 4「看看真实发生了什么」+ Chapter 5「一起决定下一步」 | A5001/A5002 独立 Review；Review 结果决定继续/调整/重判等 |
| MAINTENANCE | Chapter 5 | 低频观察、稳定条件、复发信号与再进入必须可见；不是“游戏结束” |
| CLOSED | Chapter 5 + History | Closure reason 与 Outcome 分开；历史可查看；可按规则进入 Recurrence |

说明：

- Chapter 5 可以承载 Review 后的 Maintenance / Closure / History / Recurrence 入口，但它不是新的业务终态。
- Recurrence / New Round 保留上一轮历史，根据正式业务重新进入新一轮，不做“Level 1 重置”。

---

## 2.2 Service Status 是横切层，不归属于某个 Chapter

| Service Status | 对 Journey 的关系 | IA 要求 |
|---|---|---|
| OPEN | 可处于任一正常 Case Phase | 正常展示当前合法流程 |
| WAITING | 横切多个 Chapter | 保留原 phase；明确等待原因、条件与再进入，不制造新任务 |
| LOST_CONTACT | 横切状态 | 不伪造 Outcome；历史与恢复语义保持真实 |
| SAFETY_HOLD | Safety override | 正式 Safety Authority 抢占普通体验，Growth World/普通提醒让位 |
| CLOSED | Case 终止服务状态 | 必须显示 Closure reason、Outcome 区分及历史/复发能力 |

因此 Step 2 不得把 Service Status 做成“第六个 Journey Chapter”。

# 3. Digital Use canonical flow ↔ Experience placement

## 3.1 Assessment / Formulation 前段

| Canonical nodes | 体验落点 | 不得丢失 |
|---|---|---|
| A1001 / 01002 / 01003 | Chapter 1 | Digital Use 初始 Assessment、真实选择、设备/用途/影响等当前 Authority 语义 |
| A2001 / A2002 / 01005 / 01006 / 01004 / 01000 | Chapter 1 | 分流、信息补充、严重情绪/冲突优先处理、适用测评/Consent/返回能力 |

这些节点可以在 UI 中被自然对话和少量页面承载，但不能因为“看起来像聊天”而丢失节点输入、判断、输出和记录。

## 3.2 Solution readiness / willingness / motivation

| Canonical nodes | 体验落点 | IA 必须表达 |
|---|---|---|
| A2003 | Chapter 2 | 家长期待时长、理由、已尝试方式、效果、困难 |
| A2004 | Chapter 2 | 是否愿意和孩子共同确定使用时间；YES/NO 分支真实保留 |
| A2005 | Chapter 2 | 家庭联盟 + 手机合约介绍；参与意愿 |
| A2006 | Chapter 2 | 内在动机解释；不能偷偷变成强制同意 |
| A2007 | Chapter 2 → Chapter 3 | 时间线、用户输入时间、Follow-up/提醒依据 |
| A2008 / A2009 | Chapter 2 | 不愿意/困难分支仍有真实去向，不做死路 |
| A2010 | Chapter 2 → Chapter 3 | 方案总结/Artifact 形成，进入后续两条主线的前置语义 |

重要：

> PF 确认后 Case 可以已经进入 GOALS，但 A2003–A2010 仍可按 canonical routing 合法继续。IA 不得用“当前 Phase 不等于 PF”把这些入口隐藏。

## 3.3 两条真正并行的解决主线

### Lane A — Family Alliance

`A3000–A3113`

主要承载：

- 家庭联盟原则与自评；
- 沟通准备；
- 目标清单；
- 逐目标可行性；
- 任务进度；
- 帮助/问题应对；
- 睡眠、运动、兴趣、家务、家庭活动、情绪调节、时间管理、家庭关系等已冻结目标模块。

### Lane B — Phone Use Contract

`A4001–A4012`

主要承载：

- 合约前理解；
- 模板/示范；
- A4003 成人 Simulation；
- 工具；
- 使用时长；
- 监督；
- 激励；
- 违约责任；
- 家长自我调节；
- 正式合约；
- 执行 FAQ；
- 合约更新。

冻结要求：

> 两条 Lane 在满足各自 prerequisites 后可以并行存在。Step 2 可以在视觉上给一个 Current Focus，但不能把另一条 Lane 变成不可发现、不可进入或不可恢复。

# 5. Current Focus 与 Journey Trace 的 Authority

## 5.1 Current Focus

Step 1 冻结：

> 一个主要 Current Focus + N 个仍合法的其它事项。

Step 2 冻结其技术边界：

- Current Focus 是 presentation projection，不是 Domain State；
- 但其候选合法性、blocking、Safety/Consent/Review 抢占、并行可达性不能由客户端猜；
- 服务端 application/read-model layer 必须从 authoritative snapshot 产生 viewer-scoped experience projection；
- 小程序不能通过多个 API 的本地拼接长期维护另一份 `current_focus` 真相。

服务端投影至少返回：

- primary focus；
- secondary legal items；
- blockers；
- re-entry items；
- attention signals；
- source revision / projection version。

## 5.2 Journey Trace

Journey Trace 只允许从真实业务事实派生，例如：

- Case event；
- PF / Goal / Plan version milestone；
- 真实 Scene Artifact；
- Review；
- Outcome；
- Maintenance；
- Closure；
- Recurrence。

禁止：

> 点击按钮 → 本地永久“长出一个里程碑”。

普通 UI 点击只可以产生短暂 Micro Completion；长期痕迹必须可追溯到正式 source refs。

## 5.3 Viewer-scoped

Current Focus 与 Journey Trace 都必须按：

- Visibility；
- Purpose；
- Consent；
- Authorization；
- Participation；
- Data Rights；

过滤。

视觉数量、图标、动画和历史痕迹本身也属于信息。

本节对应的正式技术合同落在 `Docs/V1技术设计.md §28.3A Frontend Experience Projection`。

# 6. Step 2 Signature Experience Moments

Step 2 的 IA 不能只“合规”，还必须主动创造四个高价值时刻。

## Moment 1 — 混乱被接住并逐渐收束

第一次进入时，不急于宣布问题是什么。

目标是：

> 用户从“我不知道怎么办”逐渐变成“我知道现在先需要弄清哪件事”。

必须允许信息不足、冲突和“暂时不知道”。

## Moment 2 — 每次回来，一眼知道一个主要 Current Focus

不是每天强造任务。

目标是：

> 用户打开产品后，很快知道现在最值得关注什么，同时其他合法并行事项仍然可发现、可进入。

WAIT / Observation / Maintenance 时可以明确：

> 现在不用做新的事情。

## Moment 3 — 系统记得仍然合法有效的上下文

产品应该让用户感到：

> “我不用每次从头解释。”

但“记得”必须服从：

- 来源；
- 当前有效性；
- 纠错；
- Consent；
- Visibility；
- Data Rights。

旧判断不得自动冒充当前事实。

## Moment 4 — Review 让真实变化变得可见

Review 不是完成率结算。

目标是帮助用户看见：

- IMPROVED；
- NO_CHANGE；
- WORSENED；
- UNKNOWN；

以及：

> 为什么下一步是继续、调整、重新判断、等待、维护、转介或 Safety。

这是产品价值最重要的“意义形成时刻”。

# 9. Step 2 当前结论

Step 2 从此不再从“后端有哪些对象，所以前端做几个栏目”开始。

正确方法是：

> **先保留完整业务真相和可达性，再把它组织成普通家庭能理解的最少界面。**

同时：

> **前端可以大幅减少用户看到的复杂度，但不能减少业务能力；可以突出一个主要焦点，但不能删除并行真实；可以设计成长和反馈，但不能自己创造永久真相。**

这就是后续 V1 Information Architecture 的设计基线。
