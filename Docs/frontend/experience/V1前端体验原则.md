# 2. Step 1 核心体验模型

为了避免前端出现过多互相重叠的模型，Step 1 正式只保留三个主要设计概念。

## 2.1 Journey Chapter

回答：

> **用户理解上，我们这一段大概在做什么？**

它是叙事层。

不是 Domain State。

## 2.2 Current Focus

回答：

> **现在最值得用户关注或完成的是什么？**

它是 Presentation Priority。

不是 Authorization。

不是业务状态。

## 2.3 Presentation Mode

回答：

> **当前界面的体验强度应该是什么？**

正式只定义：

- `Normal`
- `Reduced`
- `Serious`
- `Safety Priority`

它只用于体验表达。

不得成为新的业务状态机。

## 2.4 Feedback Event

正反馈不使用 Level 编号。

只使用四类命名事件：

### Acknowledgement

确认真实输入已经被接收。

### Micro Completion

一次有价值的小行动完成。

### Milestone

一个重要问题解决节点完成。

### Outcome Ceremony

正式 Review 支持真实阶段成果时使用。

Feedback Event 与 Presentation Mode 相互独立，但其**表现强度服从 Presentation Mode 与 Rights Neutrality Guard**：

> **Presentation Mode 与 Rights Neutrality Guard 可以降低或取消 Feedback Event 的视觉、声音、触觉或庆祝表现；Feedback Event 不得反向提升当前 Presentation Mode，也不得覆盖权利中立性要求。**

例如：

> A5001 Review 完成可以构成 Milestone，但若 Review Result = WORSENED，则只能确认 Review 已完成，不得因此播放庆祝动画或积极成长表现。

## 2.5 Experience Pacing Guidance

“接住 / 收束 / 行动 / 观察 / 复盘 / 安静”继续保留，但只作为：

> **体验节奏指导。**

它不是：

- runtime enum；
- Design Token；
- Domain State；
- 页面状态。

## 2.6 Rights Neutrality Guard

Consent、Privacy、Data Rights、Identity、Authorization 等权利场景不使用“严重程度”表达。

它们由独立的：

> **Rights Neutrality Guard**

约束。

一旦 Guard 生效：

- 不诱导；
- 不庆祝；
- 不制造损失恐惧；
- 不借成长世界推动授权；
- 不隐藏拒绝；
- 不弱化撤回；
- 不使用暗黑模式。

# 3. 整体产品体验定位

小树荫不是：

- 育儿内容平台；
- 通用 AI 聊天机器人；
- 家长控制孩子的管理工具；
- 打卡 App；
- 任务管理器；
- 儿童养成游戏；
- 单次建议生成器；
- AI 亲属；
- 长期虚拟情感伴侣。

前端核心感受应是：

> **“小树荫正在帮助我把家里这件现在很难处理的事，一步一步弄清楚、试起来、看结果，再决定下一步。”**

用户持续需要获得三个答案：

1. **我们现在大概走到哪里？**
2. **现在最值得我做什么？**
3. **真实情况有没有发生变化？**

# 4. 整体体验人格

小树荫 V1 的体验人格冻结为：

> **温和、清楚、坚定、克制。**

## 温和

不羞辱。

不把执行困难解释成道德问题。

不把孩子不同意解释成不配合。

## 清楚

让用户知道：

- 当前发生什么；
- 为什么；
- 当前能做什么；
- 当前不能做什么。

## 坚定

真正需要：

- 行动；
- Review；
- Reassessment；
- Pause；
- Referral；
- Safety；

时不使用模糊安慰拖延。

## 克制

不为了：

- DAU；
- 使用时长；
- 内容消费；
- 打开次数；
- 游戏指标；

人为制造任务、提醒、焦虑和奖励。

# 5. 原则一：问题解决旅程

## 5.1 Case 是持续的问题解决过程

用户不应该被迫管理大量后台对象。

后台可以严格存在：

- Assessment；
- Problem Formulation；
- Goal；
- Intervention；
- Plan Version；
- Task；
- Feedback；
- Review；
- Maintenance。

但用户体验应该是：

> **我们正在一起处理一件现实问题。**

## 5.2 五个用户理解章节

前端可以使用以下五个 Journey Chapter：

### 1. 先弄清楚发生了什么

用户核心问题：

> 到底怎么回事？

### 2. 决定这次先改变什么

用户核心问题：

> 这么多事情，先改变哪一个？

### 3. 一起尝试办法

用户核心问题：

> 现实里具体怎么做？

### 4. 看看真实发生了什么

用户核心问题：

> 做起来怎么样？发生了什么？

### 5. 一起决定下一步

用户核心问题：

> 继续、调整、重新判断、维护，还是进入其他路径？

## 5.3 Journey Chapter 不是业务阶段

五个章节不得替代正式：

```text
INTAKE
ASSESSMENT
PROBLEM_FORMULATION
GOALS
PLANNING
EXECUTION
REVIEW
MAINTENANCE
CLOSED
```

也不得替代独立的：

- Service State；
- Review State；
- Validity State；
- Safety；
- Authorization；
- Consent。

## 5.4 视觉聚合绝不等于业务合并

用户理解章节可以在视觉上聚合多个正式业务节点。

但是不得：

- 合并正式确认；
- 跳过正式确认；
- 合并独立授权；
- 合并独立 Review；
- 合并独立业务结果；
- 隐藏合法并行流。

特别冻结：

### Problem Formulation

必须保留正式：

> 查看 → 纠正 → 确认。

### Goal

必须保留正式确认。

### Intervention

必须让用户看到：

> 推荐什么，以及为什么。

### Plan

必须保留：

> 查看、确认、管理真实 Plan Version。

## 5.5 Digital Use 双 Review 不能被用户章节吞掉

即使用户侧都处于：

> “复盘”

这一理解章节中，

正式 Digital Use 仍必须保留：

- A5001：家庭联盟 / 目标清单 Review；
- A5002：手机使用合约 Review。

两者保持：

- 独立 eligibility；
- 独立输入；
- 独立判断；
- 独立记录；
- 独立结果。

不得因为 UI 想做：

> “一个漂亮的总复盘”

而把两个正式 Review 合并。

## 5.6 旅程不是线性通关

问题解决允许：

- CONTINUE；
- ADJUST_PLAN；
- REASSESS；
- WAIT；
- PAUSE；
- MAINTENANCE；
- REFERRAL；
- SAFETY_HOLD；
- Closure；
- Relapse / New Round。

因此禁止把产品设计成：

> Level 1 → Level 2 → Level 3 → 通关。

重新判断不是退级。

Plan 调整不是失败。

# 6. Pre-Case Entry Principle

在没有当前主要 Case 时，产品的首要任务不是提高 Engagement。

而是：

> **帮助用户以尽可能低负担、低误导的方式进入正确的问题解决流程。**

用户可以：

- 直接选择自己大概知道的问题；
- 描述“不知道属于什么问题”的情况；
- 完成必要分诊；
- 逐步确定当前主要问题。

V1 仍坚持：

> **一次只处理一个当前主要 Case。**

发现的其他候选问题可以保留。

但不能在首页形成：

> 多 Case 待办列表。

# 7. 原则二：Current Focus，而不是每日任务

## 7.1 不建立统一 Daily Task System

问题可能需要：

- 每天观察；
- 两天一次；
- 每周 Review；
- 特定事件后 Feedback；
- 一段时间不做任何新的事情。

所以：

> **Current Focus ≠ Daily Task。**

## 7.2 当前只突出一个主要焦点

首页或核心入口尽量只设置：

> **一个主要视觉焦点。**

它可能是：

- 补信息；
- 确认理解；
- 确认 Goal；
- 查看 Plan；
- 执行动作；
- 提交 Feedback；
- 完成 Review；
- WAIT；
- Reassessment；
- 获取现实支持。

## 7.3 使用 “1 + N”

体验：

> 1 个主要 Current Focus。

业务：

> N 个仍然合法的并行事项。

冻结原则：

> **体验单焦点，业务可多线程。**

## 7.4 Focus Priority Rule

Current Focus 只是：

> Presentation Priority。

它绝不是：

- Authorization；
- Eligibility；
- Domain State；
- Route Ownership。

因此一个事项成为主焦点，不能导致其他合法流失去：

- 进入能力；
- 再进入能力；
- 时间节点；
- 帮助入口；
- 业务记录；
- 独立 Review；
- 并行资格。

## 7.5 更高优先级业务可以抢占 Focus

以下状态可以使原 Current Focus 失效或让位：

- Safety；
- 必要 Consent；
- Plan invalid；
- `NEEDS_REVIEW`；
- Blocking Condition；
- Required Review；
- Referral；
- 正式业务决定的 WAIT / PAUSE。

由业务决定抢占。

前端只负责正确呈现。

## 7.6 当前行动至少解释五件事

用户需要知道：

1. 谁做；
2. 做什么；
3. 什么时候 / 什么情境；
4. 为什么；
5. 卡住怎么办。

## 7.7 行动结果不是二元成功失败

至少兼容：

- 未开始；
- 进行中；
- 部分完成；
- 完成；
- 未执行；
- 暂停；
- 取消；
- 遇到困难。

逾期不能自动变成失败。

## 7.8 “现在不用做新的事情”是正式合法体验

适用于真实：

- WAIT；
- Observation Window；
- PAUSE；
- Maintenance；
- 其他业务允许的等待状态。

不为了 DAU 人造任务。

# 8. 原则三：正反馈机制

## 8.1 不建立显性奖励经济

V1 不采用：

- XP；
- 金币；
- 等级；
- 排行榜；
- 宝箱；
- 连续签到；
- 家庭排名；
- 惩罚式 Streak。

正反馈核心：

> **告诉用户：刚刚这一步为什么有意义。**

## 8.2 奖励有效问题解决行为

值得被确认的包括：

- 真实表达；
- 表达不同意见；
- 说不知道；
- 承认没做到；
- 报告困难；
- 参与协商；
- 完成正确过程；
- 提供真实 Feedback；
- 完成 Review；
- 调整以后重新尝试；
- 中断以后回来。

## 8.3 过程进展 ≠ Outcome

完成动作：

≠ 改善。

执行率高：

≠ Intervention 有效。

家长努力：

≠ 孩子问题解决。

真正结果必须由正式 Review / Evidence 支持。

## 8.4 四类 Feedback Event

### Acknowledgement

用于：

- 提交真实信息；
- 表达不同意见；
- 未执行；
- 部分执行；
- 不知道；
- 困难反馈。

目标：

> “系统认真接住了这个事实。”

### Micro Completion

用于：

- 一个现实小行动完成；
- 一次反馈完成；
- 一次练习完成。

目标：

> “这一小步闭环了。”

### Milestone

用于：

- 形成当前问题理解；
- Goal 确认；
- 重要共同方案形成；
- 一轮 Review 完成。

目标：

> “这一段真正结束了。”

### Outcome Ceremony

只用于正式证据支持的：

- 阶段性改善；
- Maintenance；
- Stable Improvement Closure 等。

目标：

> “真实成果值得被看见。”

## 8.5 反馈必须具体

避免：

> 太棒了！

优先：

> 这一步已经记录。

> 你这次先完成了提前提醒，没有立刻继续催促。

> 这一轮暂时没看到明显改善，但我们已经知道周末是主要阻力。

## 8.6 孩子不因“服从”获得奖励

可以反馈：

- 真实表达；
- 自主参与；
- 提出困难；
- 共同协商；
- 对自己确认的约定负责。

不能奖励：

> “听家长的话。”

# 9. 原则四：失败、停滞与恢复

## 9.1 不存在统一“失败”

必须区分真实情况：

- 未执行；
- 部分执行；
- 反复困难；
- 执行充分但没变化；
- WORSENED；
- WAIT；
- PAUSE；
- UNKNOWN；
- USER_WITHDREW；
- Lost Contact；
- Referral；
- Safety。

## 9.2 一次未执行不惩罚

不使用：

- 红叉；
- 断签；
- 归零；
- “任务失败”。

只确认事实并了解情况。

## 9.3 反复困难时，从催促切换为理解阻力

系统可以询问候选解释：

- 时间不合适；
- 负担感觉太大；
- 家庭缺少配合；
- 有成员不愿意；
- 用户认为方法不适合；
- 现实条件变化；
- 说不清楚。

但这些只是：

> **candidate explanations / user input。**

## 9.4 体验层不能自行升级成正式诊断

前端 / AI 不能因为反复没做到，就直接认定：

- Intervention 不合适；
- Problem Formulation 错误；
- 用户没有动机；
- Plan 一定负担过高。

冻结边界：

> **体验层负责发现“可能需要重新看”；正式 Review / Reassessment 决定“业务上为什么”。**

## 9.5 没有效果时可以质疑方案，但不能私自定论

允许表达：

> “目前没有看到明确变化，我们需要看看是否继续、调整还是重新判断。”

不能未经正式 Review 就宣布：

> “这个 Intervention 不适合你。”

## 9.6 恶化时停止普通积极反馈

WORSENED / Safety / 重大保护条件恶化时：

- 停止庆祝；
- 停止普通成长表现；
- 信息真实性优先。

## 9.7 WAIT、PAUSE、退出和失联分开

- WAIT = 等明确条件；
- PAUSE = 暂停 Plan / Execution；
- USER_WITHDREW = 用户退出；
- Lost Contact = 正式联系状态；
- 没反馈 = UNKNOWN，不自动等于失联。

## 9.8 无债务恢复

用户中断以后回来：

不要：

- 补签；
- 补任务；
- 责备；
- 计算欠了多少。

应该：

> **从现在重新建立真实上下文。**

## 9.9 复发不是归零

过去：

- Plan；
- Feedback；
- Review；
- 有效经验；
- 无效经验；

继续存在。

新一轮不是 Level 1 重开。

# 10. 原则五：家庭角色与共同参与

## 10.1 问题是中心

不是：

> 家长管理孩子。

而是：

> **家庭中存在一个需要被共同解决的问题。**

谁需要承担改变，谁参与。

## 10.2 V1 家长主发起，孩子有限参与

V1 不强制：

- 爸爸注册；
- 妈妈注册；
- 孩子注册；
- 祖父母注册。

家长可以独立开始。

孩子按问题需要进入有限参与范围。

## 10.3 参与者不是被管理对象

孩子可以：

- 查看明确共享给自己的内容；
- 表达意见；
- 不同意；
- 拒绝参与；
- 提交 Feedback；
- 中途退出。

## 10.4 四类信息必须区分

### 本人信息

本人明确表达。

### 他人转述

必须保留转述来源。

### 共同确认内容

经过适当确认后进入共同区域。

### 私人 / 受限内容

按真实授权和用途控制。

## 10.5 转述不能升级成本人确认

妈妈说：

> 爸爸不同意。

只能表示：

> “妈妈转述爸爸可能不同意。”

不能显示：

> “爸爸不同意。”

## 10.6 每个人首先看到自己的责任

减少：

> “孩子有没有完成？”

增加：

> **“我现在能做什么？”**

家庭改变从：

> 控制别人

转向：

> 每个相关者承担自己需要改变的部分。

## 10.7 家庭分歧允许存在

妈妈：

6 小时。

孩子：

2 小时。

系统不能自动：

4 小时。

正确表达：

> 当前描述存在冲突，暂时不能确认。

## 10.8 不做家庭绩效排名

禁止：

- 妈妈完成率；
- 爸爸完成率；
- 孩子完成率；
- 谁拖后腿。

责任清楚。

评价克制。

## 10.9 共同参与使用少量“共同瞬间”

适合：

- Goal；
- 规则协商；
- Plan 共同确认；
- 关键 Feedback；
- Review。

不要求每天全家协作。

## 10.10 AI 是中立的问题解决促进者

AI 不是：

- 家庭裁判；
- 家长控制助手；
- 孩子的秘密盟友；
- 某一成员的代理人。

# 11. 原则六：心理节奏与情绪设计

## 11.1 优化适时推动，而不是活跃

产品需要知道：

- 什么时候推进；
- 什么时候退后；
- 什么时候提醒；
- 什么时候停止。

## 11.2 Experience Pacing Guidance

以下六种只作为体验指导：

### 接住

降低混乱和防御。

### 收束

帮用户抓住重点。

### 行动

提高明确性和行动能量。

### 观察

产品退后，让现实发生。

### 复盘

重新聚焦，赋予过去经历意义。

### 安静

WAIT / PAUSE / Maintenance 等状态减少刺激。

## 11.3 这些不是 runtime state

不得把：

接住 / 收束 / 行动 / 观察 / 复盘 / 安静

实现成：

- Domain Enum；
- 新 Case Phase；
- 第二套状态机。

## 11.4 提醒必须有业务目的

提醒只能服务于：

- Action；
- Feedback；
- Review；
- Re-entry；
- Maintenance Observation。

不能为了：

> “让用户回来看看。”

而存在。

## 11.5 不通过焦虑制造回访

避免：

- 连续签到即将中断；
- 还有两小时完成；
- 你三天没关注孩子问题；
- 红点轰炸；
- 虚假紧迫感。

## 11.6 温和不等于逃避现实

当正式状态要求：

- Review；
- Adjust；
- Reassess；
- Referral；
- Safety；

产品必须明确。

## 11.7 单次普通交互尽量形成短闭环

普通操作尽量一次只完成一个有意义的目标。

真正较长的：

- Review；
- Plan；
- Simulation；

应让用户提前知道需要更完整投入。

## 11.8 不使用虚假百分比

避免：

> Assessment 86%。

优先：

> 还缺一个关键信息。

或者：

> 当前信息已经足够继续。

## 11.9 阶段之间需要呼吸

完成复杂阶段后：

先：

> 整理刚刚获得了什么。

再：

> 进入下一步。

不要无限连续推进。

# 12. 原则七：成长世界与长期变化

## 12.1 不做养树游戏

不使用：

- 树等级；
- 浇水；
- 阳光币；
- 叶子数量；
- 虚拟宠物式成长。

## 12.2 核心隐喻

> **不是“养一棵树”，而是“在树荫下走过一段段真实的家庭成长旅程”。**

树是：

> 环境。

不是：

> 奖励对象。

## 12.3 双轨表达

### Journey Trace

表达：

> 我们经历了什么。

### Current Truth

表达：

> 现在实际怎么样。

两者不能混淆。

## 12.4 有效参与不能冒充改善

完成：

- Action；
- Feedback；
- Review；

可以留下旅程痕迹。

但不能因此显示：

> 问题越来越好了。

Outcome 只能来自正式业务。

## 12.5 环境三层

### 长期环境

多年维度的家庭连续体验。

### 当前旅程

当前 Case 的体验环境。

### 即时反馈

光、风、叶影、Motion、Haptics 等短反馈。

## 12.6 普通动作不永久长东西

普通 Action：

只提供即时反馈。

重要 Milestone：

才留下长期痕迹。

## 12.7 NO_CHANGE 不倒退

环境不惩罚。

真实告诉用户：

> 暂时没有看到明确变化。

## 12.8 WORSENED 不破坏世界

不：

- 枯树；
- 掉叶；
- 暴雨；
- 裂痕。

而是：

> 停止积极成长表达，转向 Reduced / Serious。

## 12.9 Safety 时成长世界退场

当正式业务 Authority 明确要求进入 `Safety Priority` 时，成长环境不得争夺注意力。

## 12.10 “一个家庭一个环境”只是概念模型

它**不等于所有成员共享一份可见世界**。

实际渲染必须是：

> **viewer-scoped projection。**

当前查看者能看到什么，必须服从：

- Visibility；
- Purpose；
- Consent；
- Authorization；
- Participation；
- Data Rights。

## 12.11 视觉本身也属于信息

以下都可能构成信息泄露：

- 里程碑数量；
- 历史路径；
- Referral 痕迹；
- Safety 痕迹；
- Case 图标；
- 环境变化；
- 某个成员留下的装饰；
- 动画状态。

所以：

> **视觉隐喻也必须经过权限过滤。**

## 12.12 删除和撤回也约束视觉派生物

如果底层信息：

- 被删除；
- Consent 被撤回；
- Visibility 变化；
- Purpose 失效；

依赖它生成的可见：

- 里程碑；
- 摘要；
- 环境痕迹；

也必须服从正式 Data Rights / Derived Data 规则。

## 12.13 V1 控制成长世界规模

只需要：

- 一个核心视觉环境；
- 少量状态变化；
- 少量长期里程碑；
- 高品质插画；
- 微动效；
- 少量 Haptics / Sound。

目标：

> **陪伴感、积累感、希望感。**

不是大型虚拟世界。

# 13. 原则八：内容、工具与 Simulation

## 13.1 不建设育儿 Feed

首页不以：

- 热门文章；
- 今日知识；
- 猜你喜欢；
- 每日课程；

作为核心。

## 13.2 所有主动内容必须回答

> **为什么现在给用户看？**

没有当前问题解决价值：

不占主界面。

## 13.3 五种情境内容

### 解释

为什么。

### 示范

怎么做。

### 练习

知道 → 会做。

### 执行工具

现实里帮助完成行为。

### 困难支持

出现阻力以后即时介入。

## 13.4 优先短、小、情境化

优先：

- 一句话；
- 30 秒解释；
- 三格漫画；
- 短动画；
- 1 分钟示范；
- 短音频；
- 短 Simulation。

长内容作为深入层。

## 13.5 用完即回到当前问题

内容结束后优先：

> 回到刚才这一步。

而不是：

> 下一篇推荐。

## 13.6 Chat 是交互方式，不是产品本体

聊天应该围绕：

- 当前理解；
- 当前 Action；
- 当前阻力；
- 当前 Review；
- 当前 Plan。

不能退化成无限开放的“家庭教育 ChatGPT”。

## 13.7 工具渐进出现

不做 18 个图标的工具超市。

优先显示当前最相关工具。

同时保留正式需求要求的再次进入能力。

## 13.8 正式 Intervention 必须同时满足全部适用 Authority Gate

一旦内容、示范、Simulation、工具或其他前端能力构成正式 Intervention，必须同时满足当前正式产品需求规定的**全部适用 Authority 条件**。

包括但不限于当前适用的：

- approved / published Professional Content；
- 有效 Psychological / Behavioral Intervention Contract；
- 当前 Formulation / Evidence prerequisites；
- 角色与年龄适用条件；
- Consent；
- Authorization；
- Safety；
- Compliance；
- 当前有效 Plan 对该 Intervention 的合法 Authority。

> **任何单一条件成立，都不能替代其他当前适用 Gate。**

UI、内容卡、解释、示范、Simulation、工具入口均不得成为绕过正式 Authority 的通道。

界面看起来轻量，不代表专业要求降低。

## 13.9 A4003 Simulation 是明确允许的例外

AI 不得以：

- 真实家庭成员；
- 长期虚拟父母；
- 长期虚拟孩子；
- 持续情感关系；

与用户建立身份关系。

但是：

> **正式需求明确授权、清楚标记为 Simulation 的一次性训练场景除外。**

A4003 必须严格遵守：

- 仅成年家长 / 监护人；
- 成年用户扮演孩子；
- AI 作为一次性家长沟通 Simulation；
- Session 显式标记 `SIMULATION`；
- 不建立长期角色人格记忆；
- 未成年人账号不得使用 AI 父母 / 监护人体验；
- 模拟内容不得写成孩子本人 Statement / Fact / Consent。

## 13.10 情境支持层

全产品允许根据需要出现：

- 解释一下；
- 看看示范；
- 练一遍；
- 用一个工具；
- 遇到困难；
- 深入了解。

但它们必须围绕：

> **当前合法问题解决上下文。**

# 14. AI 身份与生成内容透明

## 14.1 AI Identity 与 Generated Content Label 是两件事

用户知道：

> “我正在使用 AI 服务。”

不代表：

> 所有 AI 生成 Artifact 都可以不标识。

## 14.2 AI 身份必须清楚

不得让用户误以为：

- 真人专家正在聊天；
- 某个家庭成员正在回复；
- 有真实人工在后台持续处理。

## 14.3 AI 生成 / 实质改写内容按规则标识

涉及适用要求的：

- 建议；
- 文档；
- Plan Artifact；
- Summary；
- 可下载文件；
- 可复制内容；

必须保留必要 AI Generated Content 标识。

## 14.4 标识不能在导出链路静默消失

复制、下载、导出时：

必须继续服从当前正式：

- 显式标识；
- 文件元数据；
- 隐式标识；

要求。

视觉设计不能为了“更干净”把必要 provenance 删除。

# 15. 原则九：严肃场景边界

## 15.1 严肃场景包括但不限于

- WORSENED；
- Referral；
- Out of Scope；
- Safety；
- 专业不确定性；
- Invalid / NEEDS_REVIEW。

而：

- Consent；
- Privacy；
- Data Rights；
- Identity；
- Authorization；

主要由 Rights Neutrality Guard 管理。

## 15.2 Presentation Mode

### Normal

普通问题解决状态。

允许完整：

- Growth World；
- Motion；
- Feedback；
- 情境内容。

### Reduced

适合正式业务所支持的：

- NO_CHANGE；
- 反复困难；
- WAIT；
- 重要不确定性；
- 部分停滞。

减少庆祝和刺激。

### Serious

适合正式业务所支持的：

- WORSENED；
- Referral；
- Out of Scope；
- 重大业务重新判断。

环境退后。

真实信息优先。

### Safety Priority

仅当正式业务 Authority 明确要求安全状态抢占普通体验时生效。

前端不得仅凭视觉、情绪或模型自由判断自行进入该模式。

## 15.3 Safety 抢占普通体验

当正式业务状态明确要求进入 `Safety Priority` 时，包括正式 `SAFETY_HOLD`，普通体验必须让位。

此时根据正式业务 Authority：

- 普通 Plan 停止或被阻断；
- 普通 Task 停止或被阻断；
- 普通 Reminder 停止或被阻断；
- 庆祝停止；
- Growth World 退场。

前端不得自行扩大 Safety 抢占范围。

页面首先回答：

1. 发生什么；
2. 为什么普通方案不能继续；
3. 下一步是什么；
4. 系统真实能提供什么；
5. 系统不能提供什么。

## 15.4 严肃不等于恐吓

禁止：

- 满屏红；
- 警报式动画；
- 强震动；
- 恐怖天气；
- 视觉惩罚。

目标：

> **低刺激、高确定性。**

## 15.5 Referral 必须忠实映射正式 Domain Truth

Referral 前端可以把正式状态翻译成自然语言，但不得创造第二套 Referral lifecycle。

当前 V1 至少必须忠实映射：

- `PROPOSED`
- `ACCEPTED`
- `CONTACTED`
- `CONNECTED`
- `DECLINED`
- `UNREACHABLE`

用户侧文案可以自然化，但必须保持与正式状态一一可追溯。

不得把以下事实自行升级成额外 Referral 状态或“转介完成”：

- 给出资源；
- 点击资源链接；
- 用户表示愿意；
- 用户已经联系；
- `CONNECTED`。

`EXTERNAL_HANDOFF_COMPLETE` 如在正式业务中成立，只能按其正式 Closure 语义使用，不能被前端创造为第七个 Referral lifecycle state。

# 16. Rights Neutrality Guard

以下场景生效：

- Consent；
- Guardian Consent；
- Child Participation；
- Privacy；
- Data Sharing；
- Data Rights；
- Identity；
- Authorization。

冻结规则：

### 不诱导

不使用：

> “开启以后体验更完整。”

### 不隐藏拒绝

拒绝 / 暂不 / 撤回必须真实可用。

### 不制造损失恐惧

不能暗示：

> 不同意就失去成长进度。

### 不利用游戏化奖励推动授权

Consent 不产生：

- Growth Reward；
- Completion Celebration；
- Streak Benefit。

### 不情绪化阻止删除

数据删除不能使用：

> “真的舍得离开我们吗？”

### 信息可渐进披露，但后果必须清楚

严肃不等于法律条款墙。

# 17. 专业不确定性与真实表达

## 17.1 “不知道”是成熟能力

系统可以明确：

> 当前信息不足，暂时不能判断。

不是错误页。

## 17.2 冲突事实必须保留冲突

妈妈：

6 小时。

孩子：

2 小时。

不能自动生成：

4 小时。

## 17.3 NEEDS_REVIEW 必须改变前端权威表达

当对象已：

> `NEEDS_REVIEW`

前端不能继续显示为：

> 当前权威建议。

应明确表达：

> 这项内容需要重新确认，当前不能继续作为未受影响的执行依据。

# 18. V1 游戏化总原则

小树荫可以有很强的体验感。

游戏感来自：

- 清晰目标；
- 低启动成本；
- Completion Moment；
- 环境变化；
- Motion；
- Haptics；
- Sound；
- 阶段仪式；
- 长期痕迹；
- 能力成长；
- 共同确认；
- 真实反馈。

而不是：

- 金币；
- XP；
- 排行；
- Streak；
- 宝箱；
- 服从奖励；
- 儿童玩具化视觉。

冻结原则：

> **成人优先，儿童可参与；有游戏感，但没有儿童玩具感。**

以及：

> **心理学驱动体验，不进行心理操纵。**

# 19. Step 1 总体设计守则

## 19.1 复杂业务，简单感知

后台严谨。

前台自然。

## 19.2 用户理解可聚合，业务 Authority 不聚合

这是整个前端的关键边界。

## 19.3 单视觉焦点，不等于单业务线程

Current Focus 不删除合法并行路径。

## 19.4 帮用户解决问题，不让用户管理系统

用户的主要心理负担应该在现实问题。

不是在理解后台数据模型。

## 19.5 正反馈不虚构结果

过程值得被确认。

Outcome 必须真实。

## 19.6 中断可以恢复

不制造使用债务。

## 19.7 家庭共同改变，不单向控制孩子

谁需要改变，谁承担对应部分。

## 19.8 产品有张弛

该推动时推动。

该退后时退后。

## 19.9 成长世界承载时间，不承载虚假业务真相

旅程痕迹可以存在。

结果必须真实。

## 19.10 内容和工具在需要时介入

不建立内容消费 Feed。

## 19.11 权利、安全和真实服务状态拥有更高优先级

任何游戏化、增长、动效、视觉世界都不能覆盖这些边界。

# 21. Step 1 最终定义

小树荫 V1 前端不应成为：

> 一套把后台 Assessment、Goal、Plan、Task、Feedback、Review 对象逐项展示出来的管理系统。

也不应成为：

> 一套靠积分、打卡和奖励推动家长完成任务的游戏。

它应该把一套专业、长期、可追踪、可纠正、可复盘的问题解决系统，转化成：

> **普通家庭能够理解现在发生什么，知道下一步做什么，敢于真实反馈失败和困难，能够中断以后回来，能看到自己的行动留下意义，同时始终受到真实业务、安全、权限和专业边界保护的消费级产品体验。**

核心体验路径：

```text
进入并安全地找到当前真正需要处理的问题
→ 看清发生了什么
→ 确认这次先改变什么
→ 知道当前最值得做的一步
→ 获得必要的解释、示范和工具
→ 在现实生活中尝试
→ 如实记录发生了什么
→ 得到与事实一致的反馈
→ 遇到困难时理解阻力，而不是被判失败
→ 在正式 Review 中继续、调整或重新判断
→ 家庭相关成员承担各自需要改变的部分
→ 系统适时推动、适时退后
→ 时间和真实经历留下长期痕迹
→ Safety、Consent、Privacy、Referral 和真实服务状态始终拥有更高优先级
```

# 23. Step 1 Targeted Reconciliation — Experience Quality Floor

## 23.0 Revision Rationale 与状态

**当前内容状态：Step 1 Reconciled Frozen。**

本节是对已冻结 Step 1 的 **Targeted Reconciliation**，不是 Step 1 Redesign，也不是重新审计、重开产品范围或改写原有原则。

后续设计实践证明：原 Step 1 已足以阻止明显错误、越权、不安全以及把用户变成后台操作员的体验，却不足以阻止另一类结果——**业务正确、设计合规，但整体普通、平淡，用户并未真正感到自己被接住、正在推进、能够回到现实完成事情。**

因此本次仅补充**最低体验质量与关键体验验收标准**。原 Journey、Current Focus、Presentation Mode、Feedback Event、Experience Pacing、Recovery、Reality First、Rights Neutrality Guard、Safety Priority、家庭共同参与、Growth World、viewer-scoped projection、专业不确定性、AI 透明、Referral 及所有 Authority Gate 继续有效。上位产品 / 技术 Authority 始终优先。

本轮完成正式文档整合后，不再把额外独立体验审计列为本次冻结前置条件。以下均是对下游体验设计的验收约束，**不是新 Domain State、业务节点、页面、Scope 或运行时规则**。

## 23.1 Game Mechanics 克制；Game Feel 必须明显

**Game Mechanics 克制；Game Feel 必须明显。**

这里的 Game Feel 首先指用户在**正常问题解决主旅程及适用的关键体验时刻**中能感知到：

- **推进感**：复杂的现实问题逐步被理解、收束或处理；
- **回应感**：真实表达与行动确实得到符合事实的回应；
- **节奏感**：该推动时推动，该退后时退后；
- **闭合感**：一次有意义的阶段或动作有清楚的收束；
- **连续感**：用户能理解前后经历的关联，过去没有消失。

这**不要求游戏化视觉、娱乐化表达，也不要求用户意识到“这个产品像游戏”**；不意味着首页必须像游戏、每个 Completion 都必须有动画，或 Growth World 必须始终突出。第 18 节所列 Motion、Haptics、Sound、环境变化等是可能手段，**不是逐项必做的验收条件**。

以下场景不要求明显 Game Feel：Safety、Rights Neutrality、Consent、Privacy、Data Rights、Authorization、严重恶化、Referral，以及其他需要低刺激处理的严肃场景。它们优先遵守**低刺激、高确定性**；不得为“游戏感”提升刺激、掩盖事实、诱导授权或破坏退出和暂停的合法性。

## 23.2 Experience Quality Floor / 体验质量底线

**Experience Quality Floor 约束用户最终获得的体验结果，不规定设计师必须采用的表现手段。**

- 不能用“文字已经解释清楚了”替代所有体验设计。
- 反过来，卡片淡入、按钮缩放、叶子飘动、增加插画等表现手段，本身也不能证明体验质量达标。
- 每一个适用的关键体验时刻，须满足**与其心理目标和现实任务相匹配的一组必要体验结果**；不能任意命中一个结果就宣称 PASS。是否达到以用户实际理解、感受和合法行动能力为依据，不以指定动画、音效、Haptics、布局或视觉风格为依据。

对“下一步”的最终表述是：

> **接下来变得清楚。**

这可以意味着知道**接下来做什么、等什么、什么时候回来、现在可以结束本次使用，或现在可以放下 App 且不需要继续做任何事**。

**Clarity of next ≠ always another step。** 不使用“下一段自然开启”作为要求，也不为制造连续使用而添加虚假动作。必须服从 Reality First、真实 WAIT / PAUSE / Observation / Maintenance、合法退出及正式业务安排。

## 23.3 七个关键体验时刻：心理目标与验收切片

以下七项是对原 Journey / Feedback / Recovery / Reality First 的**关键体验验收切片**，不是七个页面、七个 Domain State、七个业务节点或七个强制阶段。只在当前 V1 **实际适用且进入实现范围**的时刻验收，不据此新增业务模型、流程或强制交互。

1. **从混乱到被接住**：用户的真实困扰、犹豫或“不知道”被严肃接纳，不被评判；知道系统正在帮助识别什么；不被推向未经确认的结论或额外任务。
2. **终于弄清楚当前问题**：分散信息收束为可以理解、查看、纠正、确认的当前问题理解；未知、来源冲突和专业不确定性仍被保留；用户知道为何此时可以继续或必须等待。
3. **决定这一次先改变什么**：用户理解当前真实目标、选择依据、相关责任与必要确认；知道这次先聚焦何处，而不是被迫管理多个后台对象；不吞并正式 Goal / Plan / Intervention 的 Authority。
4. **从产品进入真实行动**：用户知道谁做、做什么、何时或什么情境、为什么及遇阻怎么办；知道此时可以放下 App 回归现实；知道何时回来、等什么或本次可以结束。
5. **带着真实结果回来，包括“没做到”**：完成、部分完成、未执行、不确定和遇到困难都能如实表达并被接住；不会遭受惩罚、任务债务或虚假成功反馈；已记录的事实与正式 Outcome 判断保持分离。
6. **Review：看见真实变化并决定下一步**：用户能辨认基线、实际发生的变化、证据与不确定性；理解合法的继续、调整、重新判断、等待、暂停或退出结果；Review 完成不冒充改善，A5001 / A5002 仍各自独立。
7. **调整不是失败，回来不是重来**：调整、暂停、中断、复发后保有合法可见的历史与连续性；不补签、不清零、不追索使用债务；用户知道当前真实可行的 re-entry 或无需采取新动作。

每一项的上述结果需结合真实场景**成组成立**，不得只凭其中一句提示、单个装饰或局部微交互替代其余关键心理目标。它们不要求在所有严肃或权利场景中增加表现强度。

## 23.4 Growth World：意义放大器，而不是业务信息载体

Growth World 的正式体验职责仅为放大 Journey 的**时间感、连续感、阶段闭合感或情绪连续性**。在其适用的体验中，应对至少一项产生不可忽略的贡献：

- Journey Continuity；
- Elapsed Time；
- Milestone Closure；
- Emotional Continuity。

**Growth World 删除测试**：移除 Growth World 后，应能识别上述体验层价值的实际损失，而不能以业务能力受损来证明它有价值。可计入的“损失”**只能来自体验层的时间感、连续感、阶段闭合或情绪连续性**。

不能以损失以下内容通过删除测试：导航能力、业务信息、状态理解、完成任务所必需的信息、权限判断、Review 结果、Current Focus 或 Case Phase。

不得为了通过测试而让用户靠树判断 Case 阶段、用叶子数量表示业务进度、用环境颜色表达权限、用树的成长程度表达 Outcome，或建立第二套导航及状态系统。其渲染仍必须通过 viewer-scoped projection 和所有适用的 Data Rights / Visibility / Consent / Authorization 约束；严肃与 Safety 场景依原原则退场。

> **Growth World 是意义放大器，不是业务信息载体。**

> **Growth World 表达体验，不定义事实。**

## 23.5 正确性与体验质量分开审核

下游设计必须独立给出：

- **Correctness Gate：PASS / FAIL**
- **Experience Quality Gate：PASS / FAIL**

仅当 **Correctness Gate：PASS + Experience Quality Gate：PASS**，才允许 **Overall：PASS**。任一 FAIL 均不得用另一项的优秀表现抵消。

**Correctness Gate** 延续原有 Authority、Safety、Consent、Authorization、Domain Truth、合法路径、A5001/A5002 双 Review、Viewer Scope、Referral、Recovery、专业及合规等全部正确性检查，不因新增体验审核而降低标准。

**Experience Quality Gate** 仅检查以下**五个核心维度**，不新增评分体系、权重或第六维度：

1. **Clarity / 清晰**：用户无需研究产品结构，就知道现在发生什么、现在最值得做什么；“做什么”允许是等待、结束或不做新事。
2. **Continuity / 连续**：用户知道从哪里来、走到哪里，能感受到过去的合法经历没有消失。
3. **Emotional Response / 情绪回应**：真实行动和真实结果是否得到与事实、语境、严肃程度相符的回应；不强制积极情绪。
4. **Distinctiveness / 独特性**：**小树荫的独特性首先来自问题解决体验逻辑的组合方式，而不是界面形式的新奇程度。** 核心组合是“被接住 → 收束 → 明确一个真实方向 → 回到现实生活 → 带真实结果回来 → 非惩罚地理解困难 → Review → 延续”。不得通过非标准导航、奇怪输入方式、反常布局、为不同而不同、大量隐喻或单纯树叶、字体、插画装饰证明独特。避免 Novelty Trap。
5. **Reality Orientation / 现实导向**：体验实际支持“理解现实 → 真实行动 → 带真实结果回来 → 根据事实继续调整”，而不是让用户主要管理 App、维持活跃或完成虚构任务。

五维度用于辨认关键体验是否真正成立，不构成“任一维度命中即可通过”的清单。适用体验时刻的心理目标与现实任务优先，禁止通过总体平均分掩盖关键失败。

## 23.6 体验强度分层

**Signature Experience ≠ 每一个页面都必须特殊。**

- **核心问题解决旅程**：允许并通常需要更强的体验设计，让上述关键时刻被真实感知。
- **普通支持页面**：清楚、高效、自然即可。
- **Rights / Settings / Governance**：稳定、熟悉、低干扰、可预期；遵守 Rights Neutrality Guard。
- **Safety / Serious**：低刺激、高确定性；完整保留正式业务事实、权限与退出边界。

“不能普通”不得被解释为“每个页面都要动画、树、故事化设计”。既有 Presentation Mode 和业务 Authority 决定必要的克制程度，本节不增加新的 Mode 或视觉规范。

## 23.7 关键体验时刻的单项否决

七个关键体验时刻中，**任何已进入 V1 实现范围的核心时刻发生明显体验失败，都可以单独阻断 Experience Quality PASS**；不允许用其他页面的平均表现弥补。

但**关键体验失败必须以心理目标和现实任务是否成立判断**，不以动画、插画、Growth World、Sound、Haptics 或特殊交互是否存在判断。

例如 Reality Action 页面没有动画、没有 Growth World、视觉很简单，**不自动 FAIL**；如果用户真正知道现实里做什么、为什么、现在可以放下 App、什么时候回来或接下来等什么，完全可以 PASS。反过来，即使动画、震动、Growth World 和转场齐全，只要用户不知道现实里如何行动，**FAIL**。

本节不增加第八个关键时刻、第六个质量维度、新 Journey / 心理阶段 / Growth World 模型、体验打分或权重、动画标准、Design System、页面规则、Visual Language、Component 规范、沉浸模型或新游戏化机制。**本次仅为 Step 1 Targeted Reconciliation。**
