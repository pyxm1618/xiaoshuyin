~~~text
Correctness Gate: PASS / FAIL
+
Experience Quality Gate: PASS / FAIL

Overall PASS
=
Correctness Gate PASS
AND
Experience Quality Gate PASS
~~~

## 1A.1 Correctness Gate

- WAIT / PAUSE / LOST_CONTACT / Maintenance / CLOSED truth separation；
- History / Recurrence；
- no second frontend state machine；
- no client-authoritative business rule。

本轮 Experience Quality Reconciliation 不降低、不替代、也不重写上述检查。

- score；

# 2. V1 正式 Screen Architecture

V1 正式收敛为：

~~~text
Parent Experience
├── Home / Now
├── Progress / Journey
└── Me / Ownership

Supporting Flow
├── Pre-Case Entry
└── Focus Flow

Reused Projection
└── Historical Journey Reader
    └── reuse Progress / Journey reader

Limited Viewer Surface
└── Child Limited Participation

Global Presentation Control
├── Normal
├── Reduced
├── Serious
└── Safety Priority
~~~

这些层级不是新的业务模块，而是用户侧 projection。

## 2.1 Parent 一级结构

Parent / Guardian 一级导航固定为：

> **首页 ｜ 进展 ｜ 我的**

不得新增第四个 Parent 一级 Tab。

三者分别回答：

| 一级入口 | 用户问题 | 核心责任 |
|---|---|---|
| 首页 / Now | 现在最值得我知道或做什么？ | 当前最重要 truth + 一个主要 Current Focus |
| 进展 / Journey | 这件事怎么走到这里，现在正在发生什么？ | 当前 Case 的完整 Journey reader + 合法 1 + N 路径 |
| 我的 / Ownership | 我拥有什么、管理什么、有哪些长期权利和设置？ | Account / Family / Rights / Reminder authorization / History |

## 2.2 Supporting Flow 不是第四个模块

Pre-Case Entry 与 Focus Flow 都是 supporting flow：

- 不占 Parent 一级 Tab；
- 不形成独立长期信息架构；
- 完成 / 中断后回到 Home / Progress / Me 或现实生活；
- 不拥有业务推进 Authority。

## 2.3 Historical Journey Reader 是复用，不是第二套页面

历史入口：

> 我的 → 历史 / 过往 Case

打开后复用 Progress / Journey reader，切换为 historical read-only projection。

禁止：

- Current Case 一套 renderer；
- Historical Case 再造一套 renderer；
- 在旧 Case 中原地 reopen；
- 覆盖旧 Outcome / Closure。

Recurrence 必须来自 server-authorized linked new Case / new round。

## 2.4 Child Limited Participation 不是 Parent App 缩小版

Child 只进入 Case-specific limited surface。

它不继承 Parent：

- Home；
- Progress 全量 Journey；
- Me / Family management；
- Goal / Plan authority；
- 历史 Case；
- Parent private content。

实际可见能力始终由 viewer-scoped projection 决定。

# 3. Home / Now

## 3.1 首页唯一核心问题

首页只回答：

> **现在最值得用户知道或做什么？**

Home 不是 Dashboard。

禁止把首页组织成多个等权重后台对象卡片，例如：

- 当前阶段；
- 今日任务；
- 完成率；
- 最近进展；
- 下次 Review；
- 推荐内容；

同时争夺首屏注意力。

## 3.2 首页结构模型

首页采用：

> **1 个主要 Current Focus + N 个仍然合法的 secondary truths / entries**

即：

> **体验单焦点，业务可多线程。**

首页允许按 current truth 动态出现：

1. 当前 Journey context；
2. 一个主要 Current Focus；
3. 必要 blocking / serious / safety truth；
4. 极少量 secondary entry；
5. 通往完整 Progress / Journey 的入口；
6. viewer-authorized Growth Environment。

不要求固定六个模块永远同时存在。

## 3.3 首页不得创建 Homepage Mode

Focus / Observe / Reorient 只允许作为设计师内部构图倾向。

不得 formalize 为：

- Homepage Mode；
- runtime enum；
- frontend state；
- state machine；
- analytics truth。

正式 Presentation Mode 仍只有：

- Normal；
- Reduced；
- Serious；
- Safety Priority。

## 3.4 Current Focus 的边界

Current Focus 可以指向：

- 补充 Assessment；
- Problem Formulation 查看 / 纠正 / 确认；
- Confirm Goal；
- Intervention / Plan 查看；
- 现实行动；
- Feedback；
- A5001 / A5002 Review；
- WAIT / Observation；
- Reassessment；
- Referral / support；
- server-authorized re-entry。

Current Focus 不得：

- 取消另一条合法 stream；
- 改写 eligibility；
- 把 A2010 等同 ConfirmGoal；
- 把 A5001 / A5002 合并；
- 把 WAIT 变成任务；
- 把 Safety / Consent / Rights 变成 gamified CTA。

# 4. Progress / Journey

Progress 不是 Case Detail，也不是数据库对象列表。

它是一份可进入的 Journey reader。

## 4.1 正式阅读层级

~~~text
Journey Map
→ 我们走到哪里

Current Chapter
→ 这一段现在发生什么

Active Paths
→ 当前合法的 1 + N 路线

Journey Trace
→ 这一路真实发生过什么
~~~

这四者是阅读层级，不是四张固定 Card Module。

禁止默认实现为：

- Journey Map Card；
- Current Chapter Card；
- Active Paths Card；
- Timeline Card；

的普通 Dashboard。

## 4.2 Journey Map

Journey Map 使用 Step 1 已冻结的五章：

1. 先弄清楚发生了什么
2. 决定这次先改变什么
3. 一起尝试办法
4. 看看真实发生了什么
5. 一起决定下一步

五章只用于用户理解。

禁止：

- Journey 67%；
- Step 3 / 5；
- locked chapter；
- 把章节写入 Domain State；
- 用章节替代 Case Phase。

## 4.3 Current Chapter

Current Chapter 解释当前主要叙事语境，但不能吞掉正式业务事实。

必须保持：

- Problem Formulation：查看 → 纠正 / 补充 / 不同意 → 确认；
- Goal：正式 ConfirmGoal；
- Intervention：推荐内容 + rationale；
- Plan：Current Plan / Plan Version + current validity；
- Review：正式 Review scope / result / next action。

## 4.4 Active Paths

Active Paths 显示当前合法的 1 + N 路径。

Digital Use 必须继续独立呈现：

~~~text
Case-level Journey Narrative
≠ FAMILY_ALLIANCE position
≠ PHONE_USE_CONTRACT position
~~~

合法示例：

~~~text
整体 Journey：
一起尝试办法

FAMILY_ALLIANCE：
Execution / Feedback

PHONE_USE_CONTRACT：
Preparation / HOLD
~~~

两条 stream 不得为了视觉整齐强制同步。

A5001 与 A5002 保持：

- eligibility 独立；
- subject / version 独立；
- input 独立；
- result 独立；
- history / re-entry 独立。

用户侧可以统一用“回头看看真实发生了什么”的语言，但不能合成一个业务 Review。

## 4.5 Journey Trace

Journey Trace 回答：

> **我们经历了什么？**

可包含当前 viewer 有权看到的：

- Assessment；
- Problem Formulation；
- Goal；
- Plan Version；
- Contract Version；
- Execution / Feedback；
- WAIT；
- PAUSE；
- Review；
- Referral；
- Maintenance；
- Closure；
- 其它 server-authorized Case event。

Journey Trace 不等于 Current Truth。

历史发生过的节点可以保留，但不能因此声明当前问题正在改善。

## 4.6 Review Screen Coherence

Review screen / flow 不能仅以“信息都展示了”作为 PASS。

它必须支持用户形成连续理解：

~~~text
原来怎样 / Baseline
→ 实际发生了什么
→ Evidence / uncertainty
→ 现在我们知道什么
→ 仍然不知道什么
→ authoritative result
→ 为什么 authoritative next action 是这样
~~~

这是理解关系，不是新的 Review State Machine，也不是强制页面顺序或一个统一“总 Review”。

A5001 / A5002 必须继续保持：

- 独立 eligibility；
- 独立 input；
- 独立 result；
- 独立 history；
- 独立 re-entry。

不得为了体验连贯而合并其 Authority。

# 5. Me / Ownership

“我的”承载跨当前 Case 的长期 ownership / rights / settings。

至少包括：

- Account / Person；
- Family ownership context；
- privacy / consent management 的合法入口；
- reminder / contact authorization；
- Data Rights；
- export / correction / deletion；
- settings；
- 历史 / 过往 Case。

禁止：

- 再造 Current Case Action Center；
- 再造一套 Reminder Center；
- 将 Consent / Privacy / Data Rights 包装成 Journey achievement；
- 用 Growth World 对授权 / 撤回施压。

# 6. Pre-Case Entry

Pre-Case / First Entry 是 supporting flow，不是第四个 Parent area。

它负责：

- 真实表达 V1 当前服务范围；
- AI identity / generated content disclosure；
- 登录；
- 必要 Authorization / Privacy；
- age / guardian / applicable consent；
- 最小 Family / Person；
- Digital Use problem entry / triage。

一次只推进一个当前主要 Case。

候选问题可以保留，但首页不得出现多 Case 待办 Dashboard。

Pre-Case 不得通过 UI 勾选伪造：

- Consent；
- Legal Authority；
- Professional Approval；
- Scene eligibility。

# 7. Focus Flow

## 7.1 定义

Focus Flow 是：

> **处理当前 Current Focus 的短交互容器。**

它不是 runtime state machine。

以下词只作为 Interaction Archetypes：

- Understand；
- Confirm；
- Act；
- Reflect；
- Recover；
- Decide。

不得成为：

- runtime enum；
- authorization；
- route authority；
- business state；
- client-owned progression。

一个正式业务 Flow 可以包含多个 archetype。

## 7.2 Focus Flow 的 stable surface model

Focus Flow 可以根据任务使用：

- Inline；
- Sheet；
- Modal；
- Full Flow。

继续继承 Step 2 Surface Rule：

- Inline：低风险解释 / 小范围输入；
- Sheet：辅助选择 / detail；
- Modal：仅已有正式业务语义的简短高后果确认；
- Full Flow：Assessment、Formulation、Goal、Plan、multi-step stream、Contract、Review、Data Rights 等需要连续上下文的流程。

不得为了 UI 方便创建 generic EXIT 或新的业务确认。

## 7.3 Focus Flow 完成后

完成一件事后允许：

- 返回 Home；
- 返回 Progress；
- 返回 Me；
- 离开 App 回到现实生活。

不默认自动塞下一件任务。

“回首页”只是 navigation，不自动写：

- WAIT；
- PAUSE；
- Closure；
- Withdrawal；
- Safety Hold。

## 7.4 Meaningful Ending / Release Structural Requirement

重要 Focus Flow 不得在 Screen Architecture 层默认退化为：

~~~text
Submit
→ Success
→ Back
~~~

Screen Architecture 必须为 meaningful ending 保留体验空间，使用户能够理解：

1. 刚刚完成、确认或记录了什么；
2. 为什么这一段现在可以结束；
3. 接下来属于哪一类：
   - reality action；
   - wait；
   - return later；
   - return when condition occurs；
   - no new action；
   - lawful exit / close。

这只定义用户必须获得的结束理解，不规定 CTA 文案、页面数量、layout、card、animation 或其他 Step 4 表现手法。

继续冻结：

> **Release ≠ State。**

不得因此新增 Release enum、runtime status 或 frontend-owned progression。

# 8. 现实行动的 Screen Boundary

现实行动不是 App 内打卡。

前端应帮助用户理解：

1. 谁做；
2. 做什么；
3. 什么时候 / 什么情境；
4. 为什么；
5. 卡住怎么办。

在此基础上，Reality Action screen / flow 还必须让用户能够理解：

- 现在是否应该离开 App；
- 本次 App interaction 是否已经结束；
- 应在什么时间或条件下回来；
- 此时是在行动、等待还是无需继续；
- 不需要继续消费无关内容。

目标：

> **Action 的结束是进入现实生活，而不是进入下一个 App module。**

然后允许用户离开 App 真实行动。

这里不规定 CTA 文案、layout、button、animation、card 或 screen count。

除非正式业务确实要求，不默认采用：

> 开始任务 → 倒计时 → 点击完成

Current Focus 不是 Daily Task。

WAIT / Maintenance 也不因为 retention 需要被改造成每日任务。

# 9. Global Presentation Control

Presentation Mode 只有四种：

| Mode | 屏幕表达 |
|---|---|
| Normal | 普通 Journey / Growth / Feedback 均可正常出现 |
| Reduced | 降低庆祝和刺激，适合 NO_CHANGE、困难、WAIT、不确定性 |
| Serious | Growth World 后退，真实信息与决策优先 |
| Safety Priority | 普通体验让位于 Safety truth / next action |

这些 mode 只控制 presentation，不改变业务状态。

Rights 场景由 Rights Neutrality Guard 约束，而不是被强行分类为严重程度。

# 11. Child Limited Participation

## 11.1 基本 Flow

~~~text
Invitation
→ Understand
→ Identity Bootstrap（仅需要时）
→ Participation Decision
→ Limited Participation
→ Acknowledgement
→ Leave / Return
~~~

必须允许：

- Accept；
- Decline；
- 不同意见；
- 合法情况下“不想回答”；
- Withdraw。

Accept ≠ full Case visibility。

## 11.2 Invitation lifecycle 不得扩张

Frontend 只投影当前正式 lifecycle：

~~~text
PENDING
  → ACTIVE
  → DECLINED
  → EXPIRED

ACTIVE
  → WITHDRAWN
~~~

更准确地说：

- PENDING → ACTIVE；
- PENDING → DECLINED；
- PENDING → EXPIRED；
- ACTIVE → WITHDRAWN。

不得创建：

- CANCELLED；
- REVOKED；
- manager-cancel state；
- 前端“重新激活”。

Binding attempt lifecycle 与 invitation lifecycle 继续分离。

## 11.3 Child 可见范围

Child 只能看到 server-authorized limited projection，例如：

- 本人提交；
- 明确共享方案片段；
- 本人任务；
- 明确允许的共同内容。

不能默认读取：

- Parent private statement；
- 其他成员 private data；
- 完整 Case Journey；
- 无授权历史；
- Family management；
- Goal / Plan 全局 Authority。

## 11.4 反服从设计

禁止：

- 家长代替孩子 Accept；
- 奖励服从；
- 把不同意见当错误；
- 用 streak / badge 促进孩子长期 engagement；
- 将 withdraw 做成惩罚性退出。

# 12. Safety / Referral / Out-of-scope Surface

## 12.1 Safety

Safety Priority 抢占普通体验时：

- ordinary Current Focus 退场；
- ordinary Plan / Task / Reminder 退场或按 Authority 阻断；
- celebration 停止；
- Growth World 退场。

Safety surface 首先回答：

1. 发生什么；
2. 为什么普通方案不能继续；
3. 下一步是什么；
4. 系统能提供什么；
5. 系统不能提供什么。

禁止 dramatic warning UI：

- 满屏红；
- 强警报；
- 强震动；
- 恐怖天气；
- 特殊挑战式游戏化。

目标：

> **低刺激、高确定性。**

## 12.2 Safety cleared

正式业务转换保持：

~~~text
SAFETY_HOLD
→ ResolveRisk
→ WAITING
→ re-establish current truth
→ authoritative next action
~~~

禁止：

> Safety cleared → 自动 resume old Plan

## 12.3 Referral

Frontend 必须忠实区分：

- PROPOSED；
- ACCEPTED；
- CONTACTED；
- CONNECTED；
- DECLINED；
- UNREACHABLE。

展示电话 / 链接、用户愿意尝试、甚至用户自报已联系，都不能被包装为系统已经完成真实衔接。

## 12.4 Out-of-scope

OUT_OF_SCOPE：

- 不是 Error Page；
- 不是 Success Celebration；
- 是正式 boundary / closure context。

Surface 要清楚表达：

- 当前产品边界；
- 为什么普通路径不能继续；
- 合法下一步。

# 13. WAIT / PAUSE / LOST_CONTACT / Maintenance / CLOSED

这些必须保持为不同 truth。

## WAIT

可以真实显示：

> **现在不用做新的事情。**

并解释：

- wait reason；
- expected condition / information；
- re-entry condition。

WAIT ≠ Closure。

WAIT / Observation / Maintenance 的体验质量不只要求“没有新任务”，还要求整体产品负担真实下降，包括：

- attention load 降低；
- interaction demand 降低；
- CTA pressure 降低；
- 不要求内容消费；
- 不制造伪 engagement。

Quiet 不能只靠一句“请放心”成立；必须在体验负担上真实退后。

## PAUSE

暂停当前 Plan / execution。

PAUSE ≠ USER_WITHDREW。

## LOST_CONTACT

是正式联系状态。

一次不回复、一次通知未读或一次 Feedback 缺失不得由前端自行推成 LOST_CONTACT。

## MAINTENANCE

是 active lifecycle 的低频观察阶段。

不是 CLOSED。

## CLOSED

是正式历史状态。

必须保持：

> Case Closed ≠ Problem Improved

Closure reason 与 Outcome 分离。
