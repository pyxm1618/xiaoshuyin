# 2. Focus Flow：交互容器，不是状态机

## 2.1 Interaction Archetypes

以下只定义为 **Interaction Archetypes / 交互范式**：

- Understand；
- Confirm；
- Act；
- Reflect；
- Recover；
- Decide。

它们是设计语言，不是：

- runtime enum；
- frontend state；
- route authority；
- authorization；
- business truth。

一个正式业务 Flow 可以同时包含多个 archetype。

## 2.2 基本体验节奏

重要 Focus Flow 按需要覆盖：

~~~text
Orient
→ 为什么现在做

Engage
→ 真正的输入 / 判断 / 现实行动

Reflect
→ 接住真实结果

Meaning
→ 说明刚才这一步为什么有意义

Ending / Release Behavior
→ 明确收束，让用户回到 Home / Journey / 现实生活
~~~

这是一套体验节奏，不是业务步骤枚举。

## 2.3 Release 不是状态

不得创建：

> Release State

Release 只是 flow ending behavior。

一次 Flow 完成后：

- 可以回 Home；
- 可以回 Progress；
- 可以回 Me；
- 可以离开 App；
- 不默认自动注入下一件任务。

# 3. Key State Experience Matrix

本节描述体验语境与表达责任，不创建“一状态一页面”。

| Experience context | 用户应理解 | 主要体验责任 | 禁止 |
|---|---|---|---|
| Pre-Case / First Entry | 产品现在能处理什么、我为什么进入 | 低负担范围说明、身份/授权/必要 onboarding | 无限范围承诺、伪造 consent / eligibility |
| Assessment | 系统还在弄清发生了什么 | 渐进收集、允许 UNKNOWN / CONFLICT | 问卷打分游戏化、未完成就下结论 |
| Problem Formulation review / correction / confirmation | 这是当前理解，我可以纠正 | 看懂依据、不确定性、纠正 / 不同意 / 确认 | 把 AI 判断当事实、跳过正式确认 |
| Goal | 这次先改变什么、怎样知道有变化 | 展示 baseline / observable change / protection | 把 A2010 或 UI 点击冒充 ConfirmGoal |
| Plan | 为什么选这些办法、谁做什么 | rationale、responsibility、version、conditions | 静默覆盖 Plan Version、客户端激活 |
| Execution | 现实里怎么做 | 五要素：谁 / 做什么 / 何时何境 / 为什么 / 卡住怎么办 | 强制 App 内打卡 |
| Feedback | 真实发生了什么 | 接住事实、障碍、变化、不确定性 | pass/fail、羞辱、自动 Outcome |
| partial / not executed | 哪些发生、哪些没发生、为什么 | Acknowledgement + candidate explanation | 50% failure、红叉、streak break |
| Barrier | 可能需要重新看 | 收集解释、提供 contextual help | 客户端次数阈值升级成 Barrier / Reassessment |
| WAIT / Observation | 现在可能不用做新事 | reason、expected condition、re-entry | 人造任务、DAU 打卡 |
| Required Review | 需要正式回头看真实结果 | 清楚为什么现在 Review、scope / evidence | generic questionnaire、客户端自判 eligibility |
| Improved | 正式证据支持有改善 | Outcome truth + 克制但明确的 ceremony | 因执行完成就宣布改善 |
| NO_CHANGE | 旅程有进展，但暂未看到明确改善 | Reduced、真实说明、下一步由 Authority 决定 | 假庆祝、惩罚环境 |
| WORSENED | 结果恶化，需要严肃处理 | Serious、停止普通成长表达 | 乐观成长动画、把努力当结果 |
| Plan Adjust | 旧尝试留下，新版本继续 | 保留 Journey Trace、说明为什么调整 | 清空历史、归零 |
| PAUSE | 当前 Plan / execution 暂停 | 解释暂停事实与合法 re-entry | 当作退出 / Closure |
| Return after interruption | 先重新建立现在的 truth | no-debt re-entry、重新定位 Current Focus | 自动 resume 旧焦点、补任务 |
| Maintenance | 低频观察仍在 active lifecycle | 安静、低刺激、必要观察 | 人造 engagement |
| Closure | Case 正式结束，但不等于改善 | truthfully separate Outcome / closure reason | 所有 Closure 都庆祝成功 |
| Referral | 当前可能需要现实支持 | 忠实显示真实 referral lifecycle | 链接点击 = 已连接 |
| Out-of-scope | 当前产品边界不能继续 | 明确边界、原因、合法下一步 | Error Page、Success Celebration |
| Safety Priority | 普通体验必须让位 | 低刺激、高确定性、真实 next action | dramatic warning、游戏挑战 |
| Safety cleared → WAITING | 风险 hold 已正式解除，但旧方案尚未恢复 | re-establish current truth | 自动恢复 old Plan / Task / Reminder |
| Child invitation / identity / participation lifecycle | 这是有限、可拒绝、viewer-scoped 的参与 | 理解、身份、选择、有限参与、退出 | obedience loop、full Case visibility |

# 4. Recovery：四条正式规则

## 4.1 No Punishment

禁止：

- 红叉；
- Failure label；
- Streak break；
- 归零；
- shame；
- “你又没做到”。

一次未执行、部分执行或中断是业务事实，不是人格评价。

## 4.2 No Debt

用户中断后回来：

> **不补过去任务，不形成 catch-up queue。**

禁止：

- 补签；
- missed-task debt；
- 欠任务数量；
- 逾期惩罚；
- 连续打卡修复。

## 4.3 No Forced Resume

> **Return ≠ Resume。**

用户回来先重新建立 Current Truth。

必须重新读取 server-authorized：

- current Case status / phase；
- current Plan validity；
- current stream availability；
- Review / Safety / Consent / blocking truth；
- current viewer scope。

不得自动继续中断前的旧 Current Focus。

## 4.4 No Reset

Plan 调整、Reassessment、再次尝试：

> **不清空 Journey。**

过去的：

- Plan；
- Action；
- Feedback；
- Review；
- 有效经验；
- 无效经验；
- barrier；
- interruption；

继续作为 Journey Trace 的真实部分。

# 5. 部分完成 / 未执行

## 5.1 不机械百分比化

“做了一部分”不得默认映射：

> 50% complete

前端应关心：

1. 哪一部分发生了？
2. 哪一部分没有？
3. 为什么？
4. 有什么新情况？
5. 当前是否需要 authoritative Review / help？

## 5.2 未执行是合法 Feedback

未执行可以触发：

> **Acknowledgement**

而不是 Failure。

允许表达：

> 这次没有做成，也是一条重要信息。

但不得暗示：

> 没做也等于完成。

Process truth 仍要如实记录。

# 6. Barrier / Reassessment Authority Boundary

Frontend 可以：

- 接住未执行；
- 收集 candidate explanation；
- 呈现 contextual help；
- 告诉用户“可能需要重新看”；
- 展示 server 已给出的 blocking / reassessment requirement。

Frontend 不得：

~~~text
if missed_count >= 3:
  enter barrier
~~~

也不得创建任何类似：

- missed threshold；
- frustration score；
- engagement score；
- client-computed reassessment trigger。

正式：

- Barrier；
- Required Review；
- Reassessment；
- blocking；
- priority；

必须来自 server/domain Authority。

candidate explanation 不是正式诊断。

# 7. Process Truth 与 Outcome Truth

必须持续分开：

~~~text
执行充分
≠
结果改善
~~~

Review 表达至少同时覆盖：

## Process Truth

- 做过什么；
- 没做什么；
- 做到什么程度；
- 遇到什么；
- 哪些条件发生变化。

## Outcome Truth

- 问题是否真实变化；
- 改善 / 无变化 / 恶化 / 未知；
- 保护条件是否仍满足。

## 7.1 NO_CHANGE

允许同时表达：

> Journey 发生了进展。

以及：

> 当前没有看到明确改善。

禁止：

- 假庆祝；
- 把 Review 完成写成问题改善；
- Growth World 显示“越来越好”。

## 7.2 WORSENED

进入 Serious。

停止：

- 普通积极 Growth；
- 普通 ceremony；
- “继续加油”式假乐观；
- 用完成动作稀释真实恶化。

---

# 8. Review 不是 Generic Questionnaire

Review 是正式业务判断点，不是通用满意度问卷。

Frontend 必须保留：

- review_scope；
- subject / version；
- evidence；
- process truth；
- outcome truth；
- authoritative next action。

A5001 与 A5002：

- eligibility 独立；
- subject/version 独立；
- inputs 独立；
- result 独立；
- history / re-entry 独立。

Professional Content 未 current APPROVED/PUBLISHED 时：

- truthful unavailable / pending approval；
- 不 fake questionnaire；
- 不 fake score；
- 不 fake result；
- 不 fake REVIEW_COMPLETE。

---

# 9. Review next_action 的体验投影

Frontend 只解释 Authority 已给出的 next action。

允许：

- CONTINUE；
- ADJUST_PLAN；
- REASSESS；
- WAIT；
- PAUSE；
- MAINTENANCE；
- OUT_OF_SCOPE；
- REFERRAL；
- SAFETY_HOLD。

体验边界：

| next action | 体验表达 |
|---|---|
| CONTINUE | 继续 current work，不需要庆祝“通关” |
| ADJUST_PLAN | 说明为什么要调整，保留旧 Plan history |
| REASSESS | 回到重新理解问题，不表达退级 |
| WAIT | 明确“现在可以不做新事”，说明等待条件 |
| PAUSE | 明确暂停 current Plan，不写成退出 |
| MAINTENANCE | 降低频率、保持观察 |
| OUT_OF_SCOPE | 明确边界与合法下一步 |
| REFERRAL | 忠实显示现实支持进展 |
| SAFETY_HOLD | Safety Priority 抢占普通体验 |

用户主动退出走正式 Closure / USER_WITHDREW，不创造 generic EXIT。

# 10. Gameful Experience：嵌入，不独立成系统

V1 不建立独立游戏系统。

正式只依赖：

- Journey；
- Current Focus；
- Feedback Event；
- Growth World；
- Recovery；
- Flow Ending / Release Behavior。

禁止新增：

- Quest system；
- XP；
- Level；
- Coins；
- Badge economy；
- leaderboard；
- streak；
- family ranking；
- growth score。

Gameful 的来源是：

- 清晰目标；
- 低启动成本；
- Completion Moment；
- 环境反馈；
- 可理解的长期痕迹；
- 真实 milestone；
- 共同确认；
- 真实恢复。

而不是奖励经济。

# 11. Feedback Event

继续使用 Step 1 已冻结四类。

## 11.1 Acknowledgement

用于：

- 真实表达；
- 不知道；
- 不同意见；
- 未执行；
- 部分执行；
- 困难反馈；
- 中断后回来。

核心：

> **这个事实被认真接住了。**

Acknowledgement 不等于成功。

## 11.2 Micro Completion

用于真实小闭环，例如：

- 一个小行动完成；
- 一次 Feedback 提交；
- 一个必要输入闭环。

它不是游戏胜利。

## 11.3 Milestone

用于真正阶段节点，例如：

- Problem Formulation confirmed；
- Goal confirmed；
- 重要 Plan / shared solution 正式形成；
- A5001 / A5002 中某一个独立 Review 完成。

Milestone 只表达该真实节点完成。

## 11.4 Outcome Ceremony

只在正式 Evidence / Review 支持真实阶段结果时使用。

例如：

- server-authorized IMPROVED；
- Maintenance milestone；
- Stable Improvement Closure。

如果 Review = WORSENED：

> Review 完成可以被确认，但不得播放积极 Outcome Ceremony。

# 12. Growth World

## 12.1 正式定义

> **长期 Journey 的环境记忆，不是养成对象。**

树 / 环境是 atmosphere / memory carrier，不是 reward object。

禁止：

- 树等级；
- 浇水；
- 阳光币；
- 叶子积分；
- 任务完成树就长大；
- 问题恶化树就枯萎。

## 12.2 三层

~~~text
Long-term Environment
Current Journey Environment
Immediate Environment Feedback
~~~

### Long-term Environment

承载多年连续感和少量重要、合法的长期痕迹。

### Current Journey Environment

承载当前 Case 的 Journey context。

### Immediate Environment Feedback

光、风、叶影、轻 Motion、Haptics 等短反馈。

## 12.3 普通动作不产生长期奖励

普通 Action：

> 只产生即时反馈。

真正 Milestone / Outcome：

> 才可能留下长期痕迹。

## 12.4 Journey Trace ≠ Current Truth

~~~text
Journey Trace:
我们经历了什么

Current Truth:
现在实际怎么样
~~~

Review 完成：

> Journey 有新的真实节点。

Review = NO_CHANGE：

> Growth World 不得表达“问题越来越好”。

## 12.5 NO_CHANGE / WORSENED

NO_CHANGE：

- 环境不倒退；
- 不惩罚；
- 降低 celebration；
- truthful current truth。

WORSENED：

- 不枯树；
- 不暴雨；
- 不掉叶惩罚；
- Growth World 退后；
- Serious 真实信息优先。

# 13. Growth World Viewer Scope

视觉本身属于信息。

以下都可能泄露受限事实：

- Milestone 数量；
- 历史路径；
- Referral 痕迹；
- Safety 痕迹；
- Case icon；
- 环境变化；
- 某成员留下的 visual trace。

因此：

> **Growth World 必须是 viewer-scoped projection。**

必须服从：

- Visibility；
- Consent；
- Authorization；
- Participation；
- Purpose；
- Data Rights。

不得默认设计：

> 所有家庭成员共享同一份完整家庭成长世界。

当发生：

- Consent withdrawal；
- visibility change；
- data correction；
- deletion；
- purpose invalidation；

依赖这些数据产生的 visual derived artifacts 也必须按正式 derived-data / Data Rights 规则更新。

# 14. Motion / Haptics / Sound

本 Step 3 只冻结语义和允许场景，不冻结 Step 4 的视觉参数。

## 14.1 Motion

Motion 主要服务：

- Orientation；
- Feedback；
- Continuity。

不得用 Motion：

- 制造任务焦虑；
- 伪造 Outcome；
- 给 Safety 增加戏剧性；
- 对权利操作施压。

## 14.2 Haptics

仅在少量 meaningful moment 考虑：

- meaningful confirmation；
- Micro Completion；
- Milestone；
- Outcome Ceremony。

Safety / Rights 不默认使用强 Haptics。

## 14.3 Sound

Sound 比 Haptics 更稀缺。

只在真正值得的时刻考虑，且必须可关闭 / 服从平台与 accessibility。

禁止把小树荫做成游戏音效产品。

---

# 15. WAIT / Observation / Maintenance

这些状态必须真正允许：

> **现在不用做新的事情。**

Frontend 可以呈现：

- 为什么现在等待；
- 等什么；
- 什么时候 / 什么条件再回来；
- 用户可以主动查看什么；
- 是否有合法 reminder。

不得为了：

- DAU；
- retention；
- gamification；

人工制造：

- 每日阅读；
- 每日打卡；
- 每日“照顾成长世界”；
- 无业务意义的任务。

---

# 16. Serious / Safety

Presentation Mode 仍只有：

- Normal；
- Reduced；
- Serious；
- Safety Priority。

## 16.1 Serious

适用于正式 Authority 支持的：

- WORSENED；
- Referral；
- Out-of-scope；
- 重大重新判断。

表达：

- Growth World 后退；
- motion / celebration 降低；
- 真实信息、影响和决策优先。

## 16.2 Safety Priority

只在正式 Safety Authority 要求时进入。

普通体验让位：

- Current Focus；
- Plan；
- Task；
- Reminder；
- celebration；
- Growth World。

Safety surface 首先回答：

1. 发生什么；
2. 为什么普通方案不能继续；
3. 下一步是什么；
4. 系统能提供什么；
5. 系统不能提供什么。

目标：

> **低刺激、高确定性。**

禁止：

- 满屏红；
- 强警报；
- 强震动；
- 恐怖天气；
- 游戏化“特殊挑战”。

## 16.3 Safety cleared

正式链路：

~~~text
Safety Priority
→ formally cleared
→ WAITING
→ re-establish current truth
→ authoritative next action
~~~

禁止：

~~~text
Safety cleared
→ resume old Plan automatically
~~~

---

# 17. Referral / Out-of-scope

## 17.1 Referral

Frontend 只投影正式 lifecycle：

- PROPOSED；
- ACCEPTED；
- CONTACTED；
- CONNECTED；
- DECLINED；
- UNREACHABLE。

禁止把：

- 推荐资源；
- 展示电话；
- 点击链接；
- 用户表示愿意；
- 用户自述联系；

包装为：

> 已获得现实支持 / 已连接。

真实 handoff completion 只能来自对应 Authority / evidence。

## 17.2 Out-of-scope

Out-of-scope：

- 不是 Error；
- 不是普通 Failure；
- 不是 Completion Celebration。

体验必须明确：

- 当前边界；
- 为什么普通路径不能继续；
- 合法下一步；
- 已发生 Journey 是否仍保留。

---

# 18. Rights Neutrality

以下场景不使用 gameful pressure：

- Consent；
- Guardian Consent；
- Privacy；
- Identity；
- Authorization；
- Data Sharing；
- Participation；
- Data Rights；
- deletion / export / correction。

禁止：

- 撤回 Consent 损失成长；
- 删除数据让树枯萎；
- 情绪化挽留；
- 奖励授权；
- 同意产生 Milestone；
- 隐藏拒绝；
- 把 Rights action 当 Journey achievement。

保持：

> **平静、可预测、可理解。**

Rights Neutrality Guard 可以降低或取消 Feedback Event 的庆祝表现。

# 19. Child Limited Participation Experience

## 19.1 基本 Flow

~~~text
Invitation
→ Understand
→ Identity Bootstrap
→ Participation Decision
→ Limited Participation
→ Acknowledgement
→ Leave / Return
~~~

Identity Bootstrap 仅在正式 Authority 需要时发生；已有正确 binding 的孩子不重复走 bootstrap。

## 19.2 必须允许

- Accept；
- Decline；
- 不同意见；
- 合法情况下“不想回答”；
- Withdraw；
- 中断后 Return。

## 19.3 不允许

- Parent 代替 Child Accept；
- 奖励服从；
- 把不同意见当错误；
- 用 Growth / badge / streak 诱导授权或参与；
- 把 Child 做成长周期 engagement system；
- 向 Child 暴露 Parent 完整 Case Journey。

## 19.4 Viewer Scope

Accept：

Child experience 始终服从：

- current participation；
- authorization；
- consent；
- visibility；
- purpose；
- data rights。

## 19.5 Lifecycle truth

Frontend 不新增 participation state。

只投影：

- PENDING；
- ACTIVE；
- DECLINED；
- EXPIRED；
- WITHDRAWN。

Binding attempt outcome 与 invitation lifecycle 必须分开。

candidate 尚未合法绑定时，identity / consent / family restricted facts 的错误差异不得形成信息 oracle。

## 22.1 Problem Formulation

~~~text

→ Meaning
→ Release
~~~

## 22.2 Goal

~~~text
Orient
→ 看 baseline / desired change / observation / protection
→ user confirmation
→ server ConfirmGoal
→ Meaning
→ Release
~~~

A2010 completion 只是 server-side prerequisite 之一，不是 Goal confirmed。

## 22.3 Plan

~~~text
Orient
→ rationale / intervention / responsibilities
→ feasibility / conditions
→ user confirmation
→ authoritative ActivatePlan
→ Meaning
→ Release to real-world action
~~~

Frontend 不通过按钮本身制造 ACTIVE Plan。

## 22.4 Reality Action + Feedback

~~~text
Understand action
→ leave App / act in reality
→ return when appropriate
→ record what actually happened
→ Acknowledgement / Micro Completion if warranted
→ server-authorized next truth
~~~

不要求 countdown / check-in theatre。

## 22.5 Review

~~~text
Orient to why review now
→ Process Truth
→ Outcome Truth
→ authoritative review result
→ authoritative next action
→ appropriate Feedback Event
→ Release
~~~

Review completion 不自动等于 Outcome Ceremony。

两条 Review Flow 可以采用相似 interaction pattern，但必须保持两个独立 business instances / scope。

不得做“一个漂亮总复盘”取代两个正式 Review。

# 23. Presentation Decision Rules

允许：

~~~text
authoritative truth
→ choose presentation mode / feedback strength
~~~

禁止：

~~~text
visual mood / client heuristic / model tone
→ create business state
~~~

- WORSENED → 可使用 Serious；
- Safety Authority active → Safety Priority；

Presentation Mode 不写回 Case / Review / Safety。
