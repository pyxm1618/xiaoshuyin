# 0. V1 的唯一正确理解

## 0.1 V1 不是一个“手机问答功能”

V1 要证明的不是：

> AI 能不能回答家长几个关于手机的问题。

而是：

> **小树荫能不能依托一套可复用的问题解决系统，把一个真实家庭的儿童青少年数字使用困扰，从发现与判断，一直推进到目标、方案、执行、持续跟踪、复盘调整，并获得真实改善或正确退出。**

因此：

> **V1 = Common Problem-Solving Core + Digital Use Scene + Production-Ready Product Boundaries**

其中：

- Common Problem-Solving Core 负责所有未来场景都要复用的 Case、证据、目标、方案、任务、执行、反馈、复盘、结果、权限、安全和长期档案；
- Digital Use Scene 负责“手机 / 平板 / 电脑 / 游戏机等数字使用问题到底怎样判断、怎样选择解决路径、怎样执行和怎样评价”；
- Product Boundaries 负责真实服务必须具备的授权、隐私、持续跟踪、安全、正确退出、错误状态和真实验证。

三者缺一，V1 都不完整。

## 0.2 V1 与未来 10、20、50 个场景的关系

V1 不把系统写死成“手机系统”。

未来增加厌学、亲子冲突、学习、情绪、青春期、社交等场景时，应复用同一套 Common Problem-Solving Core，并为每个正式场景增加自己的 Scene Package。

未来新场景原则上只新增或扩展：

- Evidence / Eligibility；
- Assessment；
- Problem Formulation；
- Intervention；
- Goal；
- Plan；
- Follow-up；
- Review；
- Maintenance / Closure；
- Safety；
- Professional Knowledge。

不应为了每增加一个场景，重新建设 Case、Memory、Consent、Plan、Task、Follow-up、Review、Outcome 和 Safety 等通用机制。

## 0.3 V1 的产品完成标准

V1 不是在以下任一时点完成：

- 页面开发完成；
- AI 可以聊天；
- Assessment 问完；
- 生成了一份方案；
- 用户点击“开始执行”；
- 发出了一条提醒；
- 完成了一次任务；
- 用户说“感觉不错”。

V1 的服务闭环是：

~~~text
进入
→ 描述问题
→ 收集必要证据
→ 判断当前主要问题
→ 形成问题理解
→ 确认目标
→ 选择适用的干预路径
→ 形成可执行方案
→ 执行
→ 持续跟踪
→ 收集真实反馈
→ 复盘
→ 继续 / 调整 / 重新判断
→ 维护
→ 稳定改善 / 无需干预 / 退出 / 超范围 / 外部支持
~~~

出现信息不足、安全风险、用户拒绝、无法执行、没有改善、恶化或失联时，必须保留真实状态，不能为了走完流程伪造“完成”。

# 1. V1 用户、场景与边界

## 1.1 主要用户

V1 的主要发起用户是：

> **正在面对未满 18 岁孩子的数字使用困扰，并且不知道应该怎样处理的家长。**

数字使用包括但不限于：

- 手机；
- 平板；
- 电脑；
- 游戏机；
- 与互联网、游戏、短视频、社交、娱乐或必要学习联系相关的设备使用。

不设置未经专业依据验证的统一最低年龄。

## 1.2 参与原则

V1 采用：

> **家长可以独立开始；孩子按问题需要参与。**

孩子可以：

- 接受邀请；
- 查看明确共享给自己的内容；
- 表达本人意见；
- 对本人相关目标或任务表态；
- 提交本人反馈；
- 拒绝参与；
- 中途退出。

不要求爸爸、妈妈、孩子或祖父母全部注册。

未注册成员可以通过家长转述被记录，但：

> **转述永远不能自动升级为本人确认。**

## 1.3 V1 正式服务范围

V1 可以在“当前数字使用问题”范围内处理：

- 数字使用行为；
- 作息和睡眠；
- 必要学习与联系；
- 线下活动与行为替代；
- 家长行为；
- 家庭成员在当前问题上的一致性；
- 与当前问题直接相关的沟通和冲突；
- 当前问题中的需求、动机、能力、阻力；
- 共同规则或行动计划；
- 执行障碍；
- 持续跟踪；
- 阶段复盘；
- 方案调整；
- 维护和复发；
- 必要的孩子轻量参与。

这些内容只在“服务当前数字使用问题”所需范围内处理。

例如：

> 睡眠可以是当前手机问题的重要影响因素和行动目标。

但 V1 不因此自动提供一个完整的独立睡眠治疗产品。

## 1.4 V1 不提供

V1 不建设：

- 多个主要问题同时执行；
- 完整家庭多人私人空间；
- 其他儿童问题的完整独立干预流程；
- AI 心理或精神疾病诊断；
- 危机救援服务；
- 实时家庭调停；
- 实时语音咨询；
- 跨家庭相似案例推荐；
- 行为预测；
- 支付、订阅、退款体系；
- 机构平台；
- 全年龄服务。

如果在手机场景中发现：

> 当前真正主要的问题并不是数字使用，

系统必须停止机械执行手机方案，并进入重新判断、正确退出或现实支持路径。

# 2. Common Problem-Solving Core：V1 通用问题解决内核

本节定义未来所有正式 Scene 都应复用的产品级业务合同。

---

## 2.1 一个家庭当前只推进一个主要 Case

一个家庭可以同时存在多个候选问题，例如：

- 数字使用；
- 厌学；
- 情绪；
- 严重亲子冲突；
- 父母意见不一致。

但当前最多只有一个主要 Case 进入普通执行主线。

候选问题可以被记录，但不得偷偷开启第二条正式执行线。

需要切换主要 Case 时：

1. 说明为什么建议切换；
2. 保留原 Case 的问题理解、目标、方案、执行和结果；
3. 说明旧任务和提醒如何处理；
4. 由有权用户确认；
5. 完成切换后再启动新主线；
6. 安全状态不能通过“切走 Case”规避。

---

## 2.2 证据、陈述、事实和假设必须分开

任何用于判断的信息必须保留：

- 涉及谁；
- 谁提供；
- 发生或观察时间；
- 记录时间；
- 来源类型；
- 原始内容或引用；
- 是否已确认；
- 当前是否仍有效；
- 是否存在冲突。

至少区分：

- 本人陈述；
- 家长观察；
- 家长转述；
- 其他成员转述；
- 手工录入的设备数据；
- 工作人员记录；
- AI 假设；
- 经相应来源确认的信息。

例如：

> 妈妈说“孩子每天玩六小时”。

系统首先得到的是：

> 妈妈关于孩子数字使用时长的陈述。

不是：

> 孩子每天客观确定玩六小时。

如果孩子说“两小时”，系统允许：

> **当前存在来源冲突，暂时无法确定。**

AI 不能自己挑一个更顺眼的数字升级为事实。

---

## 2.3 允许“不知道”

V1 必须区分：

- 已知；
- 不知道；
- 尚未收集；
- 明确拒绝回答；
- 不适用；
- 来源冲突；
- 已失效。

不能把：

- 空值写成“否”；
- 未回答写成“0”；
- 家长不知道写成确定答案；
- AI 推测写成用户事实。

---

## 2.4 Case 生命周期

正常阶段至少包括：

~~~text
INTAKE
ASSESSMENT
PROBLEM_FORMULATION
GOALS
PLANNING
EXECUTION
REVIEW
MAINTENANCE
CLOSED
~~~

阶段表示：

> 正常的问题解决工作进行到哪里。

服务状态另外保存，至少包括：

~~~text
OPEN
WAITING
PAUSED
LOST_CONTACT
SAFETY_HOLD
CLOSED
~~~

阶段和服务状态不能混成一个字段。

例如：

> PAUSED + EXECUTION

表示：

> 原来正在执行，但当前暂停。

---

## 2.5 每个 Case 都必须有 Problem Formulation

Assessment 不是把问题问完就结束。

进入 Goal 前，系统必须形成一份可供用户理解和纠正的：

> **当前问题理解 / Problem Formulation。**

至少说明：

- 当前最重要的已知信息；
- 信息来源；
- 当前最可能的主要问题；
- 关键影响因素；
- 当前仍然不知道什么；
- 是否存在来源冲突；
- 为什么继续当前 Scene；
- 哪些替代解释目前不能排除；
- 哪些情况会要求重新判断或退出当前 Scene。

Problem Formulation 必须允许用户：

- 纠正；
- 补充；
- 不同意；
- 暂不确认。

没有足够依据时允许：

> 暂时无法判断。

---

## 2.6 Goal 合同

每个当前 Case 有一个主要目标，可以有多个共同服务于它的行动目标。

正式 Goal 至少包括：

- 当前基线；
- 希望发生的变化；
- 怎样观察变化；
- 观察窗口；
- 关键保护条件；
- 家长自身行动；
- 必要时孩子或其他成员的真实责任来源；
- 复盘节点。

不能把：

> “让孩子听话”

直接作为合格 Goal。

也不能只定义：

> “每天少玩两个小时”

却完全不说明睡眠、必要学习联系、家庭冲突或其他重要保护条件。

---

## 2.7 Plan 合同

正式 Plan 至少包含：

- 当前 Problem Formulation；
- Goal；
- 为什么选择这些 Intervention；
- 家长行动；
- 必要家庭协商；
- 孩子任务及其来源；
- 每项任务的责任人；
- 执行情境或时间；
- 观察方式；
- 预计阻力；
- 遇到阻力怎么办；
- Follow-up 节点；
- Review 节点；
- 调整条件；
- 暂停条件；
- Safety 条件；
- 当前 Plan Version。

方案草案、待确认方案、生效方案、已替换方案、暂停方案必须分开。

---

## 2.8 Task 与 Execution

Task 不是抽象建议。

每项任务至少说明：

- 谁负责；
- 做什么；
- 什么时候或什么情况下做；
- 需要谁配合；
- 如何判断是否执行；
- 遇到困难怎么办。

Execution 至少允许：

- 未开始；
- 进行中；
- 部分完成；
- 完成；
- 未执行；
- 暂停；
- 取消。

逾期不自动等于失败。

---

## 2.9 Follow-up

每一份生效 Plan 都必须存在：

- 下一次反馈或复盘节点；
- 当前需要用户主动返回，还是存在真实授权提醒；
- 当前实际可用渠道；
- 提醒频率和安静时间；
- 撤回方式。

提醒的意义是：

> 促成用户回来提供真实反馈。

提醒成功发送不等于：

- 用户收到；
- 用户执行；
- 结果改善。

没有提醒许可时，适用的 Plan 仍可以执行。

---

## 2.10 Feedback

Feedback 不能只问：

> 做了吗？

至少允许收集：

- 完成程度；
- 没做的原因；
- 执行中发生了什么；
- 哪个成员怎样反应；
- 实际变化；
- 新阻力；
- 新担忧；
- 新风险；
- 来源；
- 对应 Plan Version；
- 不知道；
- 不愿回答。

---

## 2.11 Review

正式 Review 必须比较：

> 基线 → Problem Formulation → Goal → Plan → 实际执行 → 实际变化 → 保护条件。

Review 需要判断至少这些可能：

- 主要是执行不足；
- 任务负担过高；
- 家庭成员没有形成必要配合；
- Intervention 选择不合适；
- 原 Problem Formulation 不完整；
- 出现新的主要问题；
- 有改善；
- 无明显变化；
- 恶化；
- 证据不足。

Review 不能只因为一个指标变好就宣布成功。

例如：

> 数字娱乐时长下降，但睡眠更差、冲突大幅升级。

不能直接记录为“方案有效”。

---

## 2.12 Review 后允许的动作

Review 后只能进入有依据的下一步：

- CONTINUE：继续当前 Plan；
- ADJUST_PLAN：调整并生成新 Plan Version；
- REASSESS：回到 Assessment / Problem Formulation；
- WAIT：等待必要信息或参与；
- PAUSE：暂停；
- MAINTENANCE：进入低强度维护；
- OUT_OF_SCOPE：当前产品不适合继续；
- REFERRAL：进入现实支持衔接；
- SAFETY_HOLD：安全中断。

实质调整必须形成新版本，不能静默修改旧 Plan。

---

## 2.13 Outcome 与 Closure 分开

Outcome 至少包括：

~~~text
IMPROVED
NO_CHANGE
WORSENED
UNKNOWN
~~~

Closure 原因至少区分：

- STABLE_IMPROVEMENT；
- NO_INTERVENTION_NEEDED；
- USER_WITHDREW；
- OUT_OF_SCOPE；
- EXTERNAL_HANDOFF_COMPLETE。

因此：

> Case 已关闭 ≠ 问题改善。

用户退出或失联也不能被统计成改善。

---

## 2.14 Maintenance 与复发

达到阶段性改善后，可以进入 Maintenance。

Maintenance 应定义：

- 当前稳定条件；
- 需要继续保持的关键行为；
- 低频观察节点；
- 复发信号；
- 重新进入 Assessment / Planning 的条件。

复发不能覆盖上一轮结果。

需要新一轮正式服务时：

> 建立与历史 Case 关联的新一轮 Case 或明确的新服务轮次。

# 3. Digital Use Scene：数字使用场景总定义

Digital Use Scene 是 V1 第一个必须真正完整的 Scene。

它不能只提供知识解释，也不能只生成一个泛化 Plan。

它必须把：

> **数字使用困扰到底是什么 → 为什么发生 → 当前真正该改变什么 → 怎样执行 → 怎样知道有没有改善**

做成完整业务流程。

---

## 3.1 Scene 的入口

用户可以：

1. 直接选择“手机 / 数字使用问题”；
2. 在总入口自然描述问题后，被初步判断可能属于 Digital Use Scene。

进入 Scene 不等于已经认定：

> 孩子“沉迷手机”或“成瘾”。

初始只建立：

> **Digital Use Concern。**

---

# 4. Digital Use Assessment：具体要了解什么

Assessment 必须由专业规则控制“哪些是必要项、条件必要项、可选项”，不能机械把所有问题一次问完。

已经从自然表达或长期档案获得且仍适用的信息，不应重复机械询问。

---

## 4.1 A 类：数字使用画像

按当前情况了解：

- 使用什么设备；
- 主要用途；
- 娱乐、社交、学习、联系等用途；
- 大致时长及来源；
- 工作日 / 休息日差异；
- 高使用时段；
- 是否经常在睡前或夜间使用；
- 停止使用是否困难；
- 是否存在反复超出原约定；
- 是否需要设备完成必要学习或联系；
- 用户是否只有估计而没有精确数据。

不以单一统一小时数直接判断问题严重程度。

如果不知道时长：

> 可以保留 UNKNOWN，必要时设计轻量观察，而不是逼用户编一个数字。

---

## 4.2 B 类：现实功能影响

需要按适用性了解：

- 入睡和睡眠；
- 起床；
- 上学；
- 作业和学习；
- 必要日常活动；
- 饮食；
- 运动；
- 线下兴趣；
- 同伴活动；
- 家庭活动；
- 家庭冲突；
- 设备停止后的实际反应；
- 是否存在其他明显功能受损。

重点不是“玩了几个小时”本身，而是：

> 数字使用与现实生活发生了什么关系。

---

## 4.3 C 类：家长和家庭当前怎样应对

至少按需要了解：

- 家长已经尝试过什么；
- 是否反复讲道理、催促；
- 是否突然没收；
- 是否删除应用；
- 是否临时加规则；
- 是否承诺后又改变；
- 家庭成员之间是否一致；
- 父母之间是否存在明显不同标准；
- 祖父母是否影响执行；
- 家长自身数字设备行为；
- 过去方法短期和长期效果；
- 目前最大的执行困难。

这些信息不是为了责怪家长，而是判断：

> 当前家庭应对方式是不是问题维持因素之一。

---

## 4.4 D 类：孩子使用数字设备可能满足的需求

系统可以提出候选假设，但不能未经证据认定动机。

按适用性探索：

- 娱乐；
- 社交；
- 同伴联系；
- 放松；
- 压力缓解；
- 成就感；
- 自主性；
- 兴趣；
- 避免无聊；
- 回避困难任务；
- 回避家庭冲突；
- 其他。

输出必须标明：

> 哪些是本人陈述，哪些是家长观察，哪些只是当前 Hypothesis。

---

## 4.5 E 类：与数字使用竞争或替代的现实活动

按需要了解：

- 睡眠；
- 运动；
- 兴趣；
- 家务；
- 家庭活动；
- 户外活动；
- 同伴线下活动；
- 时间管理；
- 其他现实活动。

目的不是机械增加“好习惯任务”，而是判断：

> 如果减少某一部分数字使用，孩子的时间、需求和获得感由什么承接。

---

## 4.6 F 类：亲子和家庭关系对当前问题的影响

只在服务当前数字使用问题所需范围内了解：

- 沟通是否仍然可能；
- 是否一谈手机就立即升级冲突；
- 孩子是否只是表面答应；
- 家长是否能够保持相对一致；
- 家长是否经常追加条件；
- 家长是否存在难以兑现的承诺；
- 是否需要另一位重要家庭成员配合；
- 孩子是否有表达空间。

如果发现：

> 严重关系问题已经成为比数字使用更主要的问题，

应重新判断当前主问题，而不是把所有关系问题都塞进手机 Scene。

---

## 4.7 G 类：其他主问题与 Safety

Assessment 过程中必须持续检查：

- 数字使用是否只是学校问题的表现；
- 是否存在明显情绪风险；
- 是否存在严重功能受损；
- 是否存在自伤、自杀、暴力或其他安全信号；
- 是否存在当前产品明显无法独立处理的问题。

命中相应条件时：

> 普通手机 Plan 不得继续机械推进。

---

# 5. Digital Use Problem Formulation

Assessment 结束前，系统不能只输出一堆答案。

必须形成 Digital Use Problem Formulation。

至少回答：

1. 目前最核心的数字使用困扰是什么；
2. 哪些证据支持；
3. 目前哪些影响最重要；
4. 家庭当前应对方式起了什么作用；
5. 数字使用可能在满足哪些需求；
6. 哪些替代解释还没有排除；
7. 当前是否适合继续 Digital Use Scene；
8. 当前最值得优先改变什么；
9. 仍需要补什么证据。

示例结构：

> 当前主要问题并不是简单“每天用了多久”，而是晚间娱乐性使用与入睡延迟、第二天起床困难和亲子冲突同时出现。家长目前主要采用反复催促和临时没收，规则不稳定。孩子本人对使用目的仍缺直接信息，因此“主要是社交需要还是压力回避”暂时不能确定。现阶段可以先围绕晚间使用、家长一致性和替代活动形成一个可观察目标，同时继续补充孩子侧信息。

用户可以：

- 确认；
- 修正；
- 不同意；
- 补充；
- 暂缓。

---

# 6. Digital Use 分诊出口

Problem Formulation 后至少存在以下出口：

## 6.1 CONTINUE_DIGITAL_USE

证据支持：

> 当前 Digital Use Scene 仍是合适主线。

进入 Goal。

## 6.2 NEED_MORE_INFORMATION

缺少真正阻止下一步判断的必要信息。

进入 WAITING 或继续 Assessment。

## 6.3 NO_INTERVENTION_NEEDED

当前证据不支持需要正式干预。

提供经过审核的解释、观察建议和返回入口，不为完成率硬造 Plan。

## 6.4 REASSESS_PRIMARY_PROBLEM

数字使用更可能是另一个主要问题的表现。

停止机械进入手机 Plan，回到主要问题判断。

## 6.5 OUT_OF_SCOPE

当前问题超出 V1 能力。

说明边界和下一步现实支持。

## 6.6 SAFETY_HOLD

Safety 优先。

普通 Digital Use Plan、普通任务和普通提醒停止。

---

# 7. Digital Use Goal

Digital Use Scene 的 Goal 不能默认等于：

> 减少总屏幕时间。

可以包含时长，但必须与当前 Problem Formulation 对齐。

可能的主要 Goal 示例：

- 改善晚间娱乐使用并恢复稳定入睡；
- 减少数字使用引发的家庭高强度冲突；
- 建立可执行的家庭数字使用共同规则；
- 减少无目的使用，同时建立能够承接需求的替代活动；
- 改善停止使用时的执行困难；
- 先完成短期观察，确认真正问题后再进入正式干预。

正式 Goal 需要满足 Common Core 的 Goal 合同。

---

# 8. Digital Use Intervention Model

这是 V1 手机场景的核心。

Digital Use Scene 不允许采用：

> “模型自由想一个方案”。

正式 Plan 必须从经过审核、版本化的 Intervention Library 中选择适用路径，再根据家庭情况组合。

V1 至少定义以下五类干预路径。

---

## 8.1 Path A：家长与家庭环境调整

旧场景资料中称为“家庭手机使用联盟”的思想，保留为一种经过重新审核后的 Intervention，而不是未经验证地宣称为唯一或最有效方法。

### 目标

建立一个更有利于数字使用改变的家庭环境。

### 可能适用

例如：

- 家庭成员标准明显不一致；
- 家长自身规则经常变化；
- 家长反复催促、临时没收；
- 家长承诺后又追加条件；
- 孩子表面答应但缺乏真实合作；
- 数字使用冲突已经被家庭互动放大。

### 可以包含

- 家长以身作则；
- 明确家庭共同规则；
- 父母之间先达成必要一致；
- 重要照护者了解规则；
- 减少临时、情绪化改变；
- 说到做到；
- 不在孩子完成原约定后随意追加条件；
- 给孩子适当表达和选择空间；
- 关注沟通中的情绪；
- 建立可持续的共同执行方式。

### 不能做

- 把“家庭联盟”当作所有家庭必须完成的固定仪式；
- 强迫所有家庭成员注册；
- 把父母不同意自动判定成家庭功能异常；
- 用羞辱、威胁、暴力或其他不安全方式换取服从。

### 输出

可以是：

> Parent / Family Action Set

而不是一定生成一份“联盟证书”。

---

## 8.2 Path B：需求承接与替代行为

旧资料中的“目标清单”保留其核心思想：

> 不能只删除手机行为，还要理解数字使用满足了什么，并考虑减少使用后由什么现实活动承接。

### 候选领域

根据证据选择，不是固定全部执行：

- 睡眠；
- 运动；
- 兴趣；
- 家务；
- 家庭活动；
- 户外活动；
- 线下社交；
- 时间管理；
- 其他适合当前家庭的现实活动。

情绪调节或家庭关系可以作为当前问题相关支持因素；如果已经成为独立主要问题，则重新分诊，不在手机 Scene 中无限扩展。

### 选择规则

不能因为某项“看起来健康”就自动加入。

必须考虑：

- 当前需求；
- 当前动机；
- 可能获益；
- 能力；
- 时间和资源；
- 阻力；
- 家长需要提供什么条件；
- 是否会增加不可承受负担。

---

## 8.3 Path C：数字使用共同规则 / 家庭计划

旧资料中的“手机使用合约”保留为一种可选的正式共同计划形式。

V1 不规定：

> 每个家庭都必须签合同。

用户拒绝“合约”形式，不阻止采用普通 ACTION_PLAN。

### 共同规则可能包含

按当前问题需要选择：

- 使用时段；
- 不使用时段；
- 使用场所；
- 夜间设备安排；
- 学习和必要联系例外；
- 娱乐使用安排；
- 如何暂停或结束；
- 家长自己的对应规则；
- 如何记录；
- 规则怎样修改；
- 发生偏差后怎样处理；
- 下次 Review 时间。

### 原则

- 尽可能让受影响成员参与；
- 条款具体；
- 责任双方化；
- 家长不能只给孩子设规则而完全忽略自身承诺；
- 规则改变要有过程；
- 不把惩罚作为默认核心；
- 不在执行后随意追加条件；
- 合约 / 共同计划可以迭代。

### 输出形式

可以是：

- Digital Use Shared Plan；
- Family Agreement；
- 普通 Action Plan。

---

## 8.4 Path D：沟通与协商支持

当 Plan 依赖真实沟通时，系统不能只告诉用户：

> “回去跟孩子好好聊聊。”

需要提供具体支持。

可能包括：

- 沟通前准备；
- 这次谈话真正要解决什么；
- 哪些内容不要一次全谈；
- 怎样表达家长自己的担忧；
- 怎样邀请孩子表达；
- 如何处理不同意；
- 如何处理“先答应后不做”；
- 如何避免反复说教；
- 如何讨论修改方案；
- 如何把冲突从“谁听谁的”转成具体可讨论的规则。

可以提供：

> AI 角色模拟 / 沟通练习。

但角色模拟只是准备工具，不能伪造孩子本人意见。

---

## 8.5 Path E：执行障碍与家长自我调节

V1 必须承认：

> 方案正确 ≠ 家庭能执行。

执行障碍可能来自：

- 目标过高；
- 任务太多；
- 家长自身情绪；
- 规则不一致；
- 家庭成员不配合；
- 孩子根本没有接受；
- 奖励或后果设计不合理；
- 现实时间资源不足；
- 原 Problem Formulation 错误；
- 新问题出现。

系统应帮助用户区分：

> 是没执行，还是方案本身不适合。

必要时提供家长自我调节、降低任务负担、重新协商、调整 Plan 或回到 Assessment 的路径。

---

# 9. Intervention Feasibility：可行性评估

任何重要 Intervention 在进入正式 Plan 前，都必须做适度可行性检查。

不要求把用户拖进巨大表格，但产品逻辑至少考虑：

| 维度 | 要回答的问题 |
|---|---|
| 具体行为 | 到底准备改变什么？ |
| 需求 | 原数字行为满足了什么？ |
| 动机 / 获益 | 新行动是否对参与者有真实意义？ |
| 能力 | 当前真的做得到吗？ |
| 时间 / 资源 | 家庭有没有条件？ |
| 阻力 | 最可能在哪失败？ |
| 家长支持 | 家长需要提供什么？ |
| 参与依据 | 谁真正同意承担任务？ |
| 负担 | 是否一次安排太多？ |
| 保护条件 | 是否可能伤害睡眠、学习、关系或其他重要事项？ |

可行性不足时：

- 降低目标；
- 换 Intervention；
- 先准备条件；
- 继续 Assessment；
- 暂缓。

不能把明显做不到的方案直接激活。

---

# 10. Digital Use Plan 形成规则

正式 Digital Use Plan 不是把所有 Intervention 都塞进去。

原则：

> **选择最少但足以验证当前 Problem Formulation 的行动组合。**

首轮通常优先少量高价值行动，避免一次改变整个家庭生活。

一个 Plan 可以组合例如：

~~~text
主要 Goal：
晚间娱乐使用结束更稳定，改善入睡，同时降低高强度冲突。

Intervention A：
父母统一晚间规则，不临时追加条件。

Intervention B：
孩子在晚间安排一个现实替代活动。

Intervention C：
共同确认夜间设备放置与必要联系例外。

Intervention D：
家长先完成一次沟通准备。

Follow-up：
三天后轻反馈，一周后正式 Review。
~~~

具体频率和周期由专业规则及家庭实际决定，不把旧资料中的统一天数自动升级为硬规则。

---

# 11. 家庭共同计划 / 合约的产品要求

如果家庭选择正式共同计划或合约形式，至少支持：

- 当前目标；
- 参与者；
- 双方各自责任；
- 使用时段 / 场所 / 用途等具体规则；
- 必要例外；
- 家长承诺；
- 孩子本人确认或明确未确认；
- 如何反馈；
- 怎样修改；
- 怎样暂停；
- Review 日期；
- 版本历史。

不能：

- 把家长代签当作孩子本人同意；
- 把合同形式当作服务资格；
- 把“盖章”等装饰功能当作核心需求；
- 因为签了合同就推断一定会执行。

---

# 12. Digital Use Execution

执行阶段的产品重点不是：

> 每天打卡制造完成率。

而是获得真实世界证据。

用户至少可以记录：

- 哪个行动做了；
- 做到什么程度；
- 没做；
- 为什么；
- 孩子如何回应；
- 家长自己有没有做到；
- 规则是否发生临时改变；
- 是否出现新的冲突；
- 睡眠等关键保护条件怎样；
- 是否有意外情况；
- 是否需要帮助。

系统要能够识别：

> 执行问题和方案问题不是一回事。

---

# 13. Digital Use Follow-up

不同阶段可以有不同 Follow-up。

例如：

- 共同计划刚开始时可以更密；
- 稳定后可以降低频率；
- 关键任务完成后立即反馈；
- 明显执行困难时提前 Review。

频率不得一刀切。

Follow-up 询问内容必须跟当前 Plan 和上次真实反馈有关，不能每次重复同一份问卷。

---

# 14. Digital Use Review

Digital Use Review 至少检查五件事。

## 14.1 行为发生了什么变化

例如：

- 使用时段；
- 夜间使用；
- 停止使用；
- 规则执行；
- 现实替代活动。

## 14.2 生活功能发生了什么变化

例如：

- 睡眠；
- 上学；
- 学习；
- 家庭活动；
- 线下活动。

## 14.3 家庭互动发生了什么变化

例如：

- 冲突增加或减少；
- 家长是否更一致；
- 是否出现新的控制—对抗循环；
- 家长自身行动是否做到。

## 14.4 原来的 Problem Formulation 还成立吗

例如：

> 原来认为主要是晚间娱乐习惯。

但执行后发现：

> 孩子主要是在回避学校压力。

这时应 REASSESS，而不是继续加码限制手机。

## 14.5 Plan 应该怎样变化

根据证据选择：

- 继续；
- 减少任务；
- 增加必要支持；
- 改变 Intervention；
- 重新协商共同规则；
- 回到 Assessment；
- 进入 Maintenance；
- 暂停；
- 转介；
- Safety。

---

# 15. Digital Use Maintenance 与稳定改善

不能只用“屏幕时间下降”判断稳定改善。

稳定改善至少应结合当前 Case 的 Goal 和保护条件。

例如可能包括：

- 关键数字使用行为改善；
- 关键生活功能没有恶化；
- 家庭冲突没有因为方案明显恶化；
- Plan 能在现实中维持；
- 家庭知道复发时怎样处理；
- 观察窗口有足够证据；
- 当前没有开放 Safety 风险。

具体专业阈值由审核后的 Scene Policy 定义，不在本 PRD 编造统一数值。

---

# 16. 旧《沉迷手机_需求文档》的继承规则

旧资料是 V1 Digital Use Scene 的重要原始产品 / 专业素材，但不是未经审核即可直接进入生产的规则文件。

## 16.1 明确保留的产品思想

本版正式继承以下业务思想：

- 先评估，再进入解决；
- 不能只讲道理；
- 需要考虑家长行为；
- 需要考虑家庭成员一致性；
- 需要理解数字使用背后的需求与获益；
- 减少数字使用后需要考虑现实行为承接；
- 目标需要做可行性检查；
- 家庭共同规则可以成为方案的一部分；
- 沟通本身需要准备和支持；
- 执行需要持续一段过程；
- 执行过程中必须处理现实障碍；
- 共同规则可以更新；
- 家庭环境与具体数字使用规则可以并行推进；
- 需要分别观察执行和结果；
- 需要持续跟踪和复盘，而不是给完建议结束。

## 16.2 不自动继承为生产硬规则

以下内容必须经过专业审核后才能进入正式 Domain Policy / Knowledge：

- 固定年龄对应固定屏幕时长；
- 仅凭时长判断“沉迷”；
- 固定 1—3 个月适用于所有家庭；
- 某一种方法“最有效”等绝对性结论；
- 未经复核的心理因果解释；
- 统一的奖励、违约、惩罚规则；
- 对严重情绪或亲子问题的越界处理；
- 未经当前证据验证的量表阈值；
- 任何可能构成诊断或治疗承诺的表述。

## 16.3 产品与专业规则分开

04 负责定义：

> 产品必须具备哪些判断、路径、用户任务和结果。

正式专业包负责定义：

> 某一条具体规则的证据依据、适用条件、排除条件和专业内容。

---

# 17. Long-term Family Record：V1 从第一天开始

V1 必须支持多年连续家庭资料。

至少保留并能按授权找回：

- 家庭和人物必要资料；
- 历史 Case；
- 原始重要陈述；
- 来源；
- Problem Formulation；
- Goal；
- 历版 Plan；
- Intervention 选择；
- Task；
- Execution；
- Feedback；
- Review；
- 哪些方法有效；
- 哪些方法无效；
- Outcome；
- Closure；
- Referral；
- 更正和失效关系。

两年、五年后回来：

> 历史不能只剩一段不可追溯的 AI 摘要。

旧信息也不能因为存在多年就自动继续当作今天的事实。

---

# 18. Authorization、Consent 与跨成员信息

## 18.1 V1 从第一天就需要基本隔离

至少区分：

- Account；
- Person；
- Family；
- Case Participant；
- Data Source；
- Visibility；
- Purpose；
- Consent。

## 18.2 家长账号不是所有信息的所有者

家长可以发起服务，但不能因此自动获得：

- 孩子未授权的私人原话；
- 其他成员的所有私人内容。

## 18.3 跨成员使用必须有用途边界

如果孩子允许：

> 信息可以用于优化共同 Plan，但不要向家长直接展示原话或来源。

系统只能在这个用途范围内形成允许的派生内容。

“脱敏”不能替代“授权”。

# 19. AI 产品边界

AI 可以：

- 理解自然表达；
- 提取候选信息；
- 提出追问；
- 总结；
- 提出 Hypothesis；
- 提出候选 Problem Formulation；
- 提出 Goal 草案；
- 从允许的 Intervention 中提出候选组合；
- 提出 Plan 草案；
- 讨论执行障碍；
- 提出 Review 建议；
- 进行沟通模拟。

AI 不能独立：

- 把 Statement 变成 Fact；
- 代替用户确认；
- 代替孩子表达本人同意；
- 修改专业规则；
- 激活未通过条件的正式 Plan；
- 解除 Safety；
- 宣称 Referral 已完成；
- 把 UNKNOWN 改成 IMPROVED；
- 关闭 Case。

---

# 20. Safety 与现实支持

Safety 是贯穿式能力。

至少在以下节点可能重新触发：

- 新输入；
- Assessment；
- Problem Formulation；
- Plan；
- Execution Feedback；
- Review；
- 恢复服务；
- 重大调整。

命中高风险后：

- 普通数字使用建议停止；
- 普通 Plan 推进停止；
- 普通任务和普通提醒按规则停止；
- 显示审核过的现实支持信息；
- 进入 SAFETY_HOLD；
- 不承诺不存在的真人即时响应。

Safety 不能因为：

> 用户下一句说“没事了”

或下一次模型判断为低风险就自动解除。

---

# 21. Referral

Referral 必须区分：

- PROPOSED：提出建议；
- ACCEPTED：用户愿意尝试；
- CONTACTED：发生真实联系；
- CONNECTED：确认建立服务衔接；
- DECLINED；
- UNREACHABLE。

点击链接不等于 CONNECTED。

推荐专业帮助也不等于问题已经改善。

# 26. V1 必须覆盖的验收案例

至少建立以下真实或受控案例作为产品验收基线。

## Case A：典型晚间数字使用 + 睡眠影响

家长报告孩子晚间持续使用设备，入睡明显推迟，并存在催促冲突。

必须验证：

- 不直接依据小时数诊断；
- 能形成睡眠、家庭应对、使用行为相关 Problem Formulation；
- 能选择少量 Intervention；
- 能进入执行和 Review。

## Case B：时长很长，但现实功能影响暂不明确

必须验证：

- 不机械生成“限时方案”；
- 能保留不确定；
- 需要时先观察；
- 可以最终走 NO_INTERVENTION_NEEDED 或继续 Assessment。

## Case C：家长说六小时，孩子说两小时

必须验证：

- 两条来源都保留；
- conflict 可见；
- 不由模型私自选择；
- Plan 不依赖虚假的确定事实。

## Case D：数字使用只是学校压力的表现

必须验证：

- Digital Use Scene 能识别主要问题可能发生变化；
- 不能继续无限加码手机规则；
- 正确回到主问题判断或退出 V1 当前能力。

## Case E：孩子拒绝签合约，但家长愿意改变

必须验证：

- 拒绝合约 ≠ 拒绝服务；
- 可以生成以家长行动为主的 ACTION_PLAN；
- 不伪造孩子同意。

## Case F：父母标准不一致

必须验证：

- 能选择家庭环境 Intervention；
- 不急于给孩子增加规则；
- 家长任务有真实责任人。

## Case G：Plan 现实上做不到

必须验证：

- 可行性检查能拦截或降低目标；
- 不把不可执行 Plan 激活；
- Review 能区分“没有意愿”和“方案负担错误”。

## Case H：屏幕时间下降但冲突和睡眠恶化

必须验证：

- Outcome 不能自动 IMPROVED；
- Review 能触发 ADJUST_PLAN 或 REASSESS。

## Case I：执行过程中出现安全信号

必须验证：

- Safety 抢占普通流程；
- 普通 Plan / 普通提醒停止；
- 不能由下一轮普通模型自动解除。

## Case J：提醒发送后用户没有反馈

必须验证：

- 发送 ≠ 触达 ≠ 执行；
- Outcome 保持 UNKNOWN；
- 不因一次不回复直接 LOST_CONTACT。

# 27. V1 成功判断

V1 不以功能列表完成作为毕业标准。

真正要验证：

1. 家庭能够完成一个真实 Digital Use Case 的问题判断；
2. Problem Formulation 有证据、有不确定性，并能被用户纠正；
3. 系统能从审核后的 Intervention Library 中形成有针对性的 Plan；
4. Plan 对真实家庭是可执行的；
5. 家长和必要成员能够实际执行；
6. 系统能够持续跟踪而不是给完方案结束；
7. 执行失败能区分是执行问题还是方案 / 判断问题；
8. Review 能真实改变后续 Plan；
9. 未改善、恶化、未知、退出、失联和转介都被如实保留；
10. 多个真实家庭出现可验证并能维持一段时间的改善案例；
11. Common Core 能支撑完整手机 Scene，而不是只有状态机；
12. 未来新增第二个 Scene 时不需要重建整个系统；
13. 没有未解决的严重安全、权限、隐私和数据越权问题；
14. 真实交付成本处于可承受范围。

小样本真实验证只能说明：

> V1 在当前样本和范围内出现了可验证结果。

不能宣传为：

> 已证明对所有家庭普遍有效。
