## 1. V1 实现目标

V1 要交付的不是“一个通用 AI 咨询框架”，而是：

> **在三层产品结构上完整实现 V1 产品需求的第一个真实纵向切片：Common Problem-Solving Core + Digital Use Scene + Production Foundation。**

家庭用户通过现有微信小程序“小树英助手”发起儿童青少年数字使用问题，在安全、授权、专业规则和真实数据约束下，完整走过：

~~~text
INTAKE
→ ASSESSMENT
→ PROBLEM_FORMULATION
→ GOALS
→ PLANNING
→ EXECUTION
→ REVIEW
→ MAINTENANCE
→ CLOSED
~~~

Digital Use Scene 不是抽象的 “assessment → plan”。V1 必须忠实实现 V1 产品需求第二层的 canonical flow：

~~~text
A1001 / 01002 / 01003
→ A2001 / A2002 / 01005 / 01006 / 01004 / 01000
→ A2003—A2010
→ 两条可并行主线
   ① A3000—A3113：家庭手机使用联盟 / 目标清单
   ② A4001—A4012：手机使用合约
→ A5001：家庭联盟 / 目标清单效果评估
→ A5002：手机使用合约效果评估
~~~

其中原文节点编号、前置条件、分支、用户输入、输出、记录、并行关系、时间线和帮助入口均由 V1 产品需求决定。技术层只负责可靠承载，不得重新编排。

V1 同时必须支持：

- Problem Formulation 作为 Goal 前的正式业务对象和正式阶段；
- Intervention 作为 Scene 的一等专业资产，不由模型临时发明；
- 家庭联盟与手机合约两条主线按 V1 产品需求并行推进；
- 目标清单、逐目标可行性、任务进度、帮助；
- 手机合约模板、4 个示范、A4003 角色扮演、合约草案/正式版本/更新、FAQ；
- 孩子按需有限参与；
- 不同来源陈述分开；
- 长期家庭档案；
- 授权和撤回；
- 安全中断；
- 正确转介；
- 模型失败；
- 长期任务和主动返回；
- 真实通知能力与 UNKNOWN；
- 并发和重复提交；
- 查看、更正、导出、删除与备份恢复后的删除重放；
- Maintenance、Closure、Recurrence。

V1 不实现：

- 完整家庭私人空间；
- 多个主要问题并行推进；
- 第二个完整专业 Scene；
- 相似案例推荐；
- 风险预测模型；
- 语音/录音输入、ASR 及实时语音；
- 实时家庭调停；
- 支付；
- 机构平台。

**完成定义：**

> 只有 V1 产品需求的 U01—U20、V1-C / V1-D / V1-X，以及 Digital Use A1001—A5002 在真实微信端、真实后端、真实权限、真实计划执行和真实 Review 中闭环，V1 才算实现。

## 4. 部署形态

V1 采用**分阶段部署**。目标是前期最低成本验证真实闭环，同时从第一天保持可平滑迁移到托管生产架构。

### Stage A — Local Development / CI

```text
Docker Compose
├─ xiaoshuyin-api
├─ xiaoshuyin-worker
├─ PostgreSQL 18
│  ├─ pgvector / sparsevec
│  ├─ pg_jieba
│  └─ pg-boss
└─ Phoenix（按需）
```

### Stage B — Early Pilot

开发完成、进入小规模邀请制真实用户后，默认使用一台 Tencent Cloud Lighthouse：

```text
Tencent Cloud Lighthouse
└─ Docker Compose / controlled images
   ├─ xiaoshuyin-api
   ├─ xiaoshuyin-worker
   ├─ PostgreSQL 18
   ├─ pg-boss
   └─ Phoenix（可按需运行）
```

约束：

- API / Worker 属于同一模块化单体、同 Repo、同领域系统；
- 使用同一受控 Docker Build，通过不同启动命令运行；
- PostgreSQL 18 仅监听本机/私有 Docker network，不开放公网数据库端口；
- 数据库数据目录使用持久卷；
- 数据库必须有自动备份、异机/对象存储副本和实际 restore 验证；
- Artifact / export / file storage 不能只依赖容器临时盘；
- Early Pilot 允许单机故障造成短暂停服，但不允许不可恢复的数据丢失；
- 本地开发与 Early Pilot 不改变 Domain / Schema / RLS / pg-boss 合同。

### Stage C — Managed Production / Growth

默认容量规划：

- 约 **300 DAU** 开始迁移演练；
- 持续约 **1,000 DAU（7-day average）** 原则上完成迁移；
- 任何资源、可靠性、合规或公开规模化运营条件提前触发时，立即提前迁移。

目标形态：

```text
微信小程序
    ↓
HTTPS
    ↓
xiaoshuyin-api
Tencent CloudBase Run Service
min instances >= 2
    ↓
TencentDB for PostgreSQL 18
    ↑
xiaoshuyin-worker
Tencent CloudBase Run Service
min instances >= 1
    ↓
pg-boss / AI / Memory / Notification Jobs
```

提前迁移条件包括：

- 单机 CPU / memory / disk / IO 已影响 API、Worker 或 PostgreSQL；
- 数据库体量、备份或恢复窗口超出 Early Pilot 可接受范围；
- 正式 SLA 需要更高 availability / RPO / RTO；
- 公开规模化获客、付费推广或单点故障风险不可接受；
- 合规/合同要求托管数据库、高可用、TDE 或更强恢复能力；
- 单机已出现影响真实家庭数据可靠性的故障。

迁移后仍然是同一个模块化单体，不是微服务重构。

### 4.0A Migration Portability Contract

V1 从第一天必须满足：

- PostgreSQL major 固定 18；Early Pilot 与 TencentDB 使用同一 Drizzle schema / migrations；
- 数据库只通过 `DATABASE_URL` + unified data layer 接入；
- Domain 不直接依赖 Lighthouse / CloudBase / TencentDB SDK；
- API / Worker 使用可移植 Docker Image；
- pg-boss、RLS、Family Memory、Professional RAG、Case、Follow-up 不依赖运行位置；
- 文件通过 Storage Adapter，不把业务长期事实写死到本地路径；
- 不使用本地 cron、共享内存、进程内锁或本地文件锁作为业务真相；
- Secret / logging / observability / backup 属于 deployment / infrastructure config。

满足该合同后，Lighthouse → CloudBase Run + TencentDB 的切换主要是：

> **PostgreSQL 数据迁移、连接串/Secret 切换、容器部署与网络/监控配置调整。**

不允许为了迁移重写 Case、Memory、RAG、Authorization、Safety、Compliance 或 Follow-up。

### 4.3 Phase-specific Security Baseline

#### Early Pilot

必须：

- PostgreSQL 不开放公网端口，仅允许本机/私有 Docker network；
- SSH 使用密钥认证与最小开放端口；
- Secret 不得进入 repo、镜像或文档；使用 deployment-time injection / root-only secret file；
- 数据库自动备份必须落到异机或对象存储，并定期做 restore 验证；
- Runtime 数据库账号仍保持非 owner、`NOBYPASSRLS`、最小权限；
- 业务日志和备份不得无控制地暴露完整家庭敏感正文。

#### Managed Production

进入 Stage C 后必须使用：

- **Tencent Cloud Secrets Manager (SSM) + KMS**；
- **CAM least-privilege role / policy**；
- **TencentDB for PostgreSQL SSL/TLS + server certificate verification**；
- **TencentDB for PostgreSQL TDE**，在创建 Managed Production 实例时启用；
- encrypted Snapshot / restore 验证。

SSM 管理数据库 Runtime Secret、模型 Key、微信 Secret 等，KMS 负责凭据与数据库加密所需密钥保护。

数据库 Secret Rotation 必须和 connection pool 的凭据刷新/重连一起演练。

若使用双账户/双凭据轮换策略：

- 两个 runtime account 权限等价且最小；
- 都不是 table owner；
- 都是 `NOBYPASSRLS`；
- Role membership / RLS behavior 一致；
- rotation 前后 API / Worker connection pool 均验证。

Always Confidential 不属于 V1 默认基线。

## 5. 领域不变量

实现必须保证：

1. Account、Person、Family、CaseParticipant 分开。
2. 一个家庭最多一个当前主要未结 Case 执行主线；其他候选 Case/问题可保留。
3. Statement、Observation、Fact、Hypothesis 分开，均保留来源、发生时间、记录时间、确认/冲突/有效性。
4. 家长转述不能自动升级为孩子本人事实。
5. KNOWN / UNKNOWN / NOT_COLLECTED / DECLINED / N/A / CONFLICTING / EXPIRED 等真实状态不能被补成确定值。
6. ASSESSMENT 之后必须进入 PROBLEM_FORMULATION；未经 Problem Formulation 不得直接 Confirm Goal。
7. Problem Formulation 必须可纠正、补充、不同意、暂不确认；变更必须版本化并传播到依赖对象。
8. Intervention 是 Scene 的一等专业资产；模型只能在已发布、适用的 Intervention 中提出候选组合。
9. Digital Use 的两条主线和 A1001—A5002 路由由 V1 产品需求决定；Common Core 和 AI runtime 不得重排。
10. AI 没有业务事实、Consent、Problem Formulation 确认、Goal 确认、Plan 激活、Contract 双方确认、Closure 或解除 Safety 的最终写权限。
11. Plan 激活必须经过 Domain Policy、依赖检查、Safety 和有权用户确认。
12. Safety Hold 优先于普通流程。
13. Outcome、Closure Reason、Referral Status 分开。
14. Follow-up Schedule 是业务真相，pg-boss Job 不是。
15. Consent 撤回必须影响后续模型、检索、通知、派生 Memory 和依赖它的 Formulation / Goal / Plan / Task。
16. 派生 Memory 必须能追到原始来源。
17. 重复提交、Worker retry 和并发不能产生重复业务结果。
18. 任何 AI run / transient context 都不能覆盖当前业务事实。
19. 只有当前 primary Case 可以进入/恢复普通执行、激活新 Plan 或创建普通 Follow-up Schedule。
20. SAFETY_HOLD 不能被普通暂停、主线切换或恢复命令覆盖。
21. 通知 SENT 不等于 DELIVERED，更不等于执行或改善。
22. A5001 与 A5002 必须保留两个 review scope，不能在数据层合并成无法区分的泛化 Review。
23. 手机合约版本不得原地覆盖；A4012 必须生成新版本并保留 supersedes 链。
24. A4003 角色扮演输出是练习/参考 Artifact，不得被写成孩子本人意见。
25. A4003 的 AI-parent 模拟只允许 adult/guardian participant；未成年人账号不得进入该模式。
26. AI 生成或实质改写的用户可见内容必须经过 Compliance Gate，不能绕过适用的 AI 身份/生成内容标识。
27. 不满 14 周岁个人信息处理没有有效 guardian consent 时，对应处理必须 BLOCK。
28. Compliance、Safety、Authorization 是独立 Gate；任一要求阻断时普通 Response/Domain Command 不得绕过。
25. V1 产品需求已融合的原始专业内容视为当前已批准 V1 基线；开发者或模型不得静默改写，生产运行必须绑定与 V1 产品需求当前版本对应的已发布 Policy / Knowledge Version。
26. 任何模型供应商都不能成为不可替换的领域依赖。
29. invitation-aware identity bootstrap 在 binding 成立前不得创建 Person、普通业务会话或 active participation；从参与邀请进入 Case C 时，必须先进 invitation-aware bootstrap，不得先调用普通 `/api/v1/auth/wechat`。普通 `/api/v1/auth/wechat` 只接收 `{ code }`，无法从新 openid 判断其是否对应某个既有 Person，因此不得要求它识别或阻断所有 Case C；no-P2 只保证 invitation-aware flow 自身不创建 P2。成功 binding 是独立身份事实，不自动创建或撤销 membership、guardian、Consent 或其他授权。


## 6. 业务状态

### 6.1 Case Status

### 6.6 Case Status 转换合同

所有状态变更必须通过 Domain Command；模型只能提出候选动作。

| 当前状态 | 命令或事件 | 必需条件 | 目标状态 | 关键副作用 |
|---|---|---|---|---|
| OPEN | WaitForInformation | 必要 blocker 非空 | WAITING | 保留原 phase；停止不适用推进 |
| WAITING | ResumeAfterInformation | blocker 实际清除，重新检查 Authorization / Safety / Package | OPEN | 回到原 phase；重新计算有效 schedule |
| OPEN/WAITING | PauseCase | 有权用户明确请求或交付条件要求 | PAUSED | 暂停普通未来 schedule |
| PAUSED | ResumeCase | primary、授权、Safety、Policy、Plan 均重新有效 | OPEN/WAITING | 不补发过期提醒 |
| OPEN/WAITING | MarkLostContact | 至少两个约定反馈节点无反馈 + 至少一次真实授权联系尝试 | LOST_CONTACT | 停止普通自动联系；保留主动返回 |
| LOST_CONTACT | UserReturned | 新输入已保存并重新 Safety / Consent 校验 | OPEN/WAITING | 创建新的有效 schedule |
| 任意未关闭 | EnterSafetyHold | Safety Policy 命中 | SAFETY_HOLD | 抑制普通生成、任务推进和提醒 |
| SAFETY_HOLD | ResolveRisk | 规定复核证据和有权角色完成 | WAITING | 不自动恢复旧任务 |
| 允许关闭状态 | CloseCase(...) | 对应 Closure 合同满足 | CLOSED | phase 同时置 CLOSED；取消未来普通 schedule |
| CLOSED | CreateRecurrence | 用户发起复发/新一轮且重新检查授权 | 新关联 Case | 旧 Case 保持不可变历史 |

LOST_CONTACT 不能由“一次不回复”“通知失败”“用户没有通知授权”推断。

Referral 独立流转：

~~~text
PROPOSED --用户接受--> ACCEPTED
ACCEPTED --真实联系尝试--> CONTACTED
CONTACTED --有实际衔接证据--> CONNECTED
任意阶段 --用户拒绝--> DECLINED
CONTACTED --真实合规尝试仍失败--> UNREACHABLE
~~~

点击链接、发送通知、创建工单均不能直接升级为 CONNECTED。

### 6.7 正常 Phase 转换合同

| 当前 Phase | 命令 | 核心前置条件 | 目标 Phase |
|---|---|---|---|
| INTAKE | StartAssessment | primary；必要授权；至少一条可追溯问题陈述；Safety 未阻断 | ASSESSMENT |
| ASSESSMENT | PresentProblemFormulation | Assessment 已达到当前可形成判断的最小证据；冲突/未知明确 | PROBLEM_FORMULATION |
| PROBLEM_FORMULATION | ConfirmProblemFormulation | 用户已看到 formulation；可纠正/补充/不同意；必要信息足够；scene fit 仍成立 | GOALS |
| PROBLEM_FORMULATION | ReassessFromFormulation | 用户纠正、冲突或替代解释要求重新判断 | ASSESSMENT |
| GOALS | ConfirmGoal | Goal 合同完整；Safety 未阻断 | PLANNING |
| PLANNING | ActivatePlan | Formulation / Goal / Intervention / Plan 依赖有效；家长确认 | EXECUTION |
| EXECUTION | OpenReview | 到达 review 节点或主动触发；允许 UNKNOWN | REVIEW |
| REVIEW | CompleteReview(CONTINUE) | Review 完整且不需改 Plan | EXECUTION |
| REVIEW | CompleteReview(ADJUST_PLAN) | 实质调整有依据 | PLANNING |
| REVIEW | CompleteReview(REASSESS) | 主要问题理解出现实质变化 | ASSESSMENT |
| REVIEW | EnterMaintenance | 改善趋势和保护条件支持低强度观察 | MAINTENANCE |
| MAINTENANCE | MaintenanceReview(CONTINUE) | 维护条件仍满足 | MAINTENANCE |
| MAINTENANCE | MaintenanceReview(RELAPSE_OR_WORSEN) | 复发/恶化/保护条件失效 | ASSESSMENT 或 PLANNING，由 Policy 决定 |
| MAINTENANCE | CloseCase(STABLE_IMPROVEMENT) | 稳定改善证据、观察窗口、保护条件、用户确认 | CLOSED |

统一规则：

- 从 ASSESSMENT 到 GOALS **不得跳过 PROBLEM_FORMULATION**；
- UNKNOWN、WORSENED 或保护条件恶化不能直接进入 MAINTENANCE / STABLE_IMPROVEMENT；
- WAITING 保存原 phase；恢复后回到原 phase；
- Phase 变化、对应业务写入、Follow-up Schedule 与需要立即创建的 pg-boss job，通过 Drizzle transaction + pg-boss adapter 位于同一 PostgreSQL transaction；不使用独立 Job Outbox；
- primary 与 Safety 统一守门适用于 Resume、Confirm Formulation、Confirm Goal、Activate Plan、Review 后继续推进；
- Digital Use 内部 A/010xx 节点推进不等同于全局 Phase；节点路由由 Scene Package 管理。

### 7.0 Drizzle、主键与 Migration 合同

### 7.1 身份与授权

~~~text
accounts
persons
families
family_members
consent_records
case_participants
staff_assignments
~~~

身份与家庭归属的基数由本节固定。列级字段与约束写法由实现决定，但不得改变下列基数：

- **Account ↔ Person = 1 : 1。** 一个 Account 只对应一个 Person；一个 Person 最多绑定一个 Account，可以为空。数据库约束必须能阻止「一个 Account 对应多个 Person」与「一个 Person 绑定多个 Account」。
- **Person ↔ Family = 多对多，只经 `family_members` 表达。** 不得在 `persons` 上使用 `family_id` 之类的单家庭绑定；否则「一个 Person 属于多个 Family」无法表达。
- **`family_members` 至少唯一表达 (family, person)。** 同一个 Person 可以存在于多个 Family；同一个 Person 在同一个 Family 不得有重复 membership。
- `family_members` 只表达「Person 属于哪个 Family」，不是 guardian 事实源。V1 不引入 guardian / non-guardian 角色枚举，也不引入 admin / owner / child / member 通用角色 DSL 或 RBAC。

**受邀既有 Person 的身份绑定**

- 参与邀请指向的既有 Person 分两种情形。**Case B**：P1 已有 Account B；当前已认证 Account 就是 B 时直接复用既有 binding，不重新绑定、不进入 identity bootstrap，继续参与说明 / accept / decline；当前已认证 Account 不是 B 时拒绝，不 rebind、不替换。**Case C**：P1 尚没有 Account，才进入 invitation-aware identity bootstrap。
- invitation-aware identity binding 只改变 Case C 的 `Person → Account` 的 0..1 关系，不创建 Person、Family、`family_members` 或 guardian reference。
- Case C 绑定前 P1 的 Account 必须为空；绑定后仍满足 Account ↔ Person 1:1 与 Person → Account 0..1，不得 rebind 或替换既有绑定。
- 如果 candidate 已独立完成普通登录（Account A 已绑定既有 Person P2），之后打开 P1 的邀请，则 invited binding 必须拒绝：保持 A↔P2 与 P1 不变，不得 merge / delete / rebind，也不得为 P1 创建 active participation。该内部结果记为 identity conflict；V1 不解决 duplicate Person recovery。
- V1 只支持 P1 当前仅属于目标 Family 的情形；同一 P1 存在多个 Family membership 时必须 BLOCK。`family_members` 的 schema 级多对多继续保留，但 V1 不因此提供多家庭切换、跨家庭身份关联、家庭合并或共享身份管理。
- 成功 binding 是独立身份事实；之后 participation decline / withdraw、Case close、guardian consent revoke 或其它下游授权撤销，不自动解除 Account↔Person 绑定。

`guardian_person_id` 是 V1 中 guardian relationship 的唯一基线，它与 Family membership 相互独立：

- 一个人是某家庭成员，不因此成为该家庭未成年人的 guardian；

- V1 当前一个未成年人只保存一个有效 guardian 引用。多 guardian、joint custody、guardian 多对多与 guardian 历史关系不是 V1 数据要求，需要时再显式升级本文。

**Invited identity binding 的 guardian 语义**

- 本合同中的 guardian relationship 等同 `P1.person_compliance_profiles.guardian_person_id`；它是 current guardian reference，不是 Family membership 角色。产品需求中的「当前 guardian / 当前 guardian 关系 / 当前监护人同意」均投影到该字段与对应 guardian consent 记录，产品文档不直接使用存储字段名。
- second-party guardian confirmation 的 actor 必须满足：authenticated Account → Account's Person = P1 当前 `guardian_person_id`。不得仅凭客户端声明 guardian Person ID。
- 对 UNDER_14，还必须满足 current valid guardian consent，且该 consent 对应的 guardian 与当前 `guardian_person_id` 一致。
- **second-party confirmation = target confirmation + candidate recognition**。candidate recognition 指：confirmer 基于与 P1 既有的现实家庭关系，独立辨认当前这次已认证微信身份的实际使用者就是 P1。它必须独立于 invite token possession、nickname / displayName、Family membership、客户端声称与系统自动推断，且必须由人工作出。具体 pairing / attestation interaction mechanism 由后续 Plan 在本合同已批准的 family-attested scope 内设计；Plan MAY 设计临时 challenge、pairing interaction、confirmation workflow、anti-replay、token / crypto 实现，但 MUST NOT introduce KYC、government-ID verification、facial recognition / face verification、phone-based identity matching、video identity verification 或其它新的外部身份证明 / 敏感数据来源，除非有新的上游合同评审与批准。本文只冻结「必须对 candidate 本人作独立识别并明确 attestation」，不枚举具体技术候选。
- 该识别是 family-attested identity association，不是 KYC、不是 legal identity verification，也不是 government identity proof；合同、验收与产品文案不得宣称达到实名 / KYC 强度。
- `person_compliance_profiles.verified_source` **不是** guardian identity-proof 字段，也不等于 guardian relationship verification source。不得利用它发明新的 guardian verification subsystem。
- guardian relationship ≠ Family membership；guardian consent ≠ identity-binding confirmation；identity-binding confirmation ≠ Consent grant。

**Pre-consent 与正式 Person 分离**

`person_compliance_profiles` 以 `person_id` 引用 Person，因此它只能存在于正式未成年 Person 合法成立之后。对 UNDER_14：

- 有效监护人同意成立前，不得先创建完整正式 child Person / child profile，再事后补 consent；
- `create child Person → collect profile → obtain consent later` 不是正常路径，也不得作为实现上的默认顺序；
- 如果为完成 consent 流程确需保存最小状态，只能保存 consent onboarding 严格必要的最小状态 / 证据，不得在该状态中承载 Assessment / Case / Digital Use / AI 所需的孩子资料；
- 该最小状态的技术表达（表、键、token / session 或等价形式）由后续实现 Plan 决定；本文不预先建表，也不在本文定义 onboarding API。

## 9. Authorization & Consent

每次读写统一调用：

```text
authorize({
  actor,
  product,
  family,
  case,
  resource,
  action,
  purpose
})
```

权限检查至少同时考虑：

- 当前身份；
- 家庭关系；
- Case 参与关系；
- 数据可见范围；
- Consent；
- Purpose；
- staff assignment；
- Safety 规则。

客户端传入的：

`family_id`、`case_id`

只能作为：

> 待验证参数。

不能因为 ID 存在就允许访问。

因为一个 Person 可以属于多个 Family，授权必须按「当前目标 Family」判定：

- 家庭权限来自 actor 在当前目标 Family 的 membership，不得由 Person 本身推导出唯一家庭；
- guardian relationship 不等于 family access：guardian 引用只用于未成年人 Compliance Gate，不能替代家庭成员关系；
- V1 当前的管理主体是创建该 Family 的 adult Account / Person；其他家庭成员不因此获得默认的成员管理权限；
- V1 不建设多管理员与家庭成员角色权限矩阵，成员管理权限不得按角色表推导。

**Identity-binding authorization boundary**

- identity-binding confirmation 是独立 Gate，不是 membership、guardian relationship 或 Consent。
- 第二方 confirmation 的语义是 **target confirmation + candidate recognition**：确认者必须基于与 P1 既有的现实家庭关系，独立辨认当前已认证微信身份的实际使用者就是 P1，而不是仅批准 invitation / binding request。
- 第二方确认主体按年龄矩阵确定：UNDER_14 必须是当前 `guardian_person_id` 的已认证 Account / Person；MINOR_14_17 有 `guardian_person_id` 时同样必须是该 guardian，仅在不存在时允许目标 Family 的 V1 管理主体确认；ADULT 不支持；UNKNOWN 阻断。Family 管理主体若无法独立辨认 candidate 就是该 Family 所知的既有 Person，必须 BLOCK；管理权限本身不构成 candidate recognition。
- binding 成功只建立 Account↔Person；不授予 Family / Case / Participant / Visibility / Purpose / Consent。后续每个访问仍由 `authorize()` 按当前目标 Family、Case participation、Consent、Purpose 与 Safety 独立判定。
- guardian confirmation 不得写成 guardian consent；identity-binding confirmation 不得写成 Consent record。
- pending authentication context 不是 Person，也不是家庭作用域身份；不得凭它读取任何家庭数据。
- 在 candidate 尚未成功绑定为 P1 之前，candidate-facing response 必须与内部真实结果分离：内部可保留 `PENDING_SECOND_CONFIRMATION` / `INELIGIBLE` / `IDENTITY_CONFLICT` / `CONSENT_BLOCKED` / `MULTI_FAMILY_BLOCKED` / `INVITATION_EXPIRED` 等真实原因（具体枚举名留 Plan），对外必须是不可区分的 generic「binding not completed」，不得透露 guardian 是否存在、同意是否有效、年龄分类、多 Family、Person 是否存在、目标 Family 归属或 Account 绑定的存在性。
- 已授权的第二方确认者 / 管理主体可以在其自身授权上下文看到完成确认所必需的信息；该可见性不得扩散给 candidate 或未授权主体。

### 9.1 PostgreSQL RLS：数据库最后一道家庭隔离

应用层 `authorize()` 是业务权限事实；PostgreSQL RLS 是防止查询遗漏导致跨家庭泄漏的第二道硬防线，不能互相替代。

数据库账号必须分离：

```text
xiaoshuyin_migrator
- table owner
- 执行 migration / DDL
- 不作为应用 runtime

xiaoshuyin_app
- 非 table owner
- NOBYPASSRLS
- 仅应用运行权限
```

核心家庭数据表必须显式：

```sql
ALTER TABLE ... ENABLE ROW LEVEL SECURITY;
ALTER TABLE ... FORCE ROW LEVEL SECURITY;
```

并由 migration / CI 校验 `pg_class.relrowsecurity = true` 与需要的 `relforcerowsecurity = true`。

所有家庭级读写必须通过统一 `withRlsTransaction(authContext, fn)`。在同一个 `db.transaction()` / connection 内，使用参数化 `set_config(..., true)` 设置 `app.family_id`、`app.person_id`、`app.purpose` 等上下文，再执行全部业务 SQL 和必要的 pg-boss enqueue。

禁止：

- 在事务外先 `SET LOCAL` 再从连接池执行查询；
- 用 `sql.raw` 拼接 family/person/purpose；
- 使用 table owner / BYPASSRLS runtime role；
- 因为 RLS 已存在就跳过 `authorize()`。

RLS policy 对可选上下文使用安全转换，例如：

```sql
family_id = NULLIF(current_setting('app.family_id', true), '')::uuid
```

无上下文时默认拒绝，而不是放行。

因为 Person 与 Family 是多对多，`app.family_id` 必须是当前请求的目标家庭，不得由 `app.person_id` 反查或反推出唯一家庭；`family_members` 上的策略同样以当前 `family_id` 与 actor 在该家庭的 membership 为准，而不是以 person 的单家庭归属为前提。

pending authentication context 不是家庭作用域读取：在 identity binding 成立前，它不得设置 `app.family_id`、不得读取家庭数据、不得签发普通业务会话。其技术表达与 RLS 交互由后续 Plan 定义；本轮不改任何 RLS policy。

## 10. V1 的孩子参与

孩子参与采用有限 Case Participant。

进入孩子端前必须读取服务端 Compliance Profile：

- age_band；
- minor_mode；
- guardian relationship；
- guardian consent version；
- 当前 feature access policy。

不满 14 周岁且缺少有效监护人同意时，不得继续对应个人信息处理或 AI 交互。

**Consent gate 顺序（UNDER_14）**

```text
adult actor established
→ guardian / consent onboarding
→ valid guardian consent
→ create formal child Person
→ create child compliance state
→ downstream processing
```

不得把：

```text
create child Person
→ collect profile
→ obtain consent later
```

作为正常路径或实现上的默认顺序。

**Gate 边界**

UNDER_14 无有效监护人同意时，必须阻断正式 child profile 的建立以及后续个人信息处理。

但完成合法监护人同意本身所严格必要的最小处理，不被这个 gate 自己锁死；该最小处理的边界见 §7.7A。本设计不因此新增 consent staging table、token / session schema 或 onboarding API，最小技术表达在对应实现 Plan 中决定。

**参与路径分流：Case B 与 Case C**

```text
邀请指向的既有 Person P1

if P1 已有 Account：
    Case B
    if 当前已认证 Account == P1 的 Account：
        → 复用既有 binding，不进入 identity bootstrap
        → 查看本次参与说明 → 接受 / 拒绝
    else:
        → 拒绝（不 rebind、不替换、不创建 active participation）

else（P1 无 Account）：
    Case C
    → invitation-aware identity bootstrap（下）
```

已有正确 Account 的孩子不得被要求重新走双确认 binding。

**Case C 身份引导顺序**

```text
家长创建邀请
→ target 打开邀请（invite possession ≠ identity proof）
→ A. Phase A — independent WeChat authentication：
   微信认证完成 → temporary pending authentication context
   （此时不得把 candidate 身份与 P1 关联；无 P1-specific candidate confirmation、
     无 P1-specific second-party recognition request、无 Person / 无普通会话 / 无 active participation）
→ Gate 1 — applicable Age / Compliance pre-gate（在任何 P1-specific processing 之前）：
   先解析 age_band
   UNDER_14：核验 P1 合法存在、当前 guardian relationship、当前有效 guardian consent、
             适用 Compliance gate 允许该最小身份绑定处理
   MINOR_14_17：核验 P1 合法存在、applicable Compliance gate；UNDER_14 guardian consent
                不是仅因年龄施加的前置，其它 applicable Consent / Compliance 仍必须通过
   ADULT / UNKNOWN：终止
   （失败 → generic non-disclosing result；不建立 candidate↔P1 关联、
     不记录 P1-specific candidate confirmation、不请求 P1-specific second-party recognition）
→ Phase B — 建立临时 binding-attempt association 后，candidate 针对 P1 的明确确认
→ 请求 second-party confirmation（同一 binding attempt；invitation / attempt 仍有效）
→ 第二方确认 = target confirmation + candidate recognition
→ Gate 2 — commit 前复核：age / applicable Compliance、当前 guardian、当前 consent、
   invitation validity、confirmation authority、candidate recognition、Account / Person conflicts
→ Account A ↔ existing Person P1（exactly once）
→ 普通 authenticated identity
→ 查看本次参与说明 → 接受 / 拒绝 → 获得当前 Case 的有限权限
```

- Case C 必须走独立的 invitation-aware capability；从参与邀请进入时不得先调用普通 `/api/v1/auth/wechat` 创建第二个 Person。
- Phase A 只证明「某个微信身份完成认证」，不得把 candidate 身份与 P1 关联，不得记录 P1-specific candidate confirmation，不得请求 P1-specific second-party recognition，也不得签发普通业务会话或产生活跃参与。
- Gate 1 通过后，允许建立临时的 binding-attempt 关联（candidate 已认证身份 + P1 + invitation context + binding attempt），用于 candidate 针对 P1 的确认、第二方 candidate recognition、attempt 审计与 commit 资格判断；该关联不是 Account↔Person binding，不是普通已认证身份，不是 active participation，不授予任何业务授权。Phase A「不得与 P1 关联」的限制不延伸到该 Phase B 关联。
- UNDER_14 的 Gate 1 不得省略：在 Gate 1 通过前不得建立 candidate↔P1 关联事实、不得记录针对 P1 的 candidate confirmation、不得展示 P1 专属信息或请求 P1 专属第二方确认。读取既有 Consent / Compliance 状态以执行 Gate 1，属于执行合规门禁的必要处理，不是新增未经授权的业务处理。
- Gate 1 通过不豁免 Gate 2；任一门禁在 commit 前失效，binding 必须阻断。
- 两方确认必须指向同一 binding attempt，且都必须在其 invitation / binding attempt 仍有效时完成。
- candidate recognition 在 UNDER_14 由当前 guardian 作出；MINOR_14_17 有 guardian 时由该 guardian，否则由目标 Family 的 V1 管理主体作出。确认者无法独立辨认 candidate 就是 P1 时必须阻断；管理权限、membership、昵称与系统推断不能替代该辨认。
- binding 成功后，participation decline / withdraw、Case close、guardian consent revoke 或其它下游授权撤销不自动解绑；只阻断受影响的下游处理与参与能力。

**未绑定 candidate 的响应分离**

```text
internal result ≠ candidate-observable result
```

- 内部可保留真实业务状态（PENDING_SECOND_CONFIRMATION / INELIGIBLE / IDENTITY_CONFLICT / CONSENT_BLOCKED / MULTI_FAMILY_BLOCKED / INVITATION_EXPIRED 等；enum 名留 Plan）。
- 在 candidate 尚未成功绑定为 P1 之前，candidate-facing response 必须统一为不可区分的 generic「binding not completed」。不得透露 guardian 是否存在 / 缺失、consent 是否有效、年龄分类、是否多 Family、Person 是否存在、目标 Family 归属或其他 Account 绑定。
- 「可以继续做什么」也不能成为 oracle：不得出现「错误 candidate 看到等待 guardian，而 consent 无效者看到已拒绝」这类差异。具体 HTTP status / error code / envelope 由 Plan 决定。
- 已授权第二方 / 管理主体可在其自身授权上下文看到完成其任务所必需的信息。

**绑定尝试生命周期与参与邀请生命周期**

```text
Invitation lifecycle ≠ Binding attempt lifecycle
```

业务结果封闭为四类：

| 结果 | 含义 |
|---|---|
| COMMITTED | binding 成功，Account A ↔ P1 建立。 |
| PENDING | attempt 仍合法，正在等待尚可合法补齐的 confirmation / permitted step。 |
| TERMINAL ATTEMPT REJECTION | 该 attempt 永远不能再次成功。 |
| RETRYABLE OPERATION FAILURE | operation timeout、未知网络结果、临时基础设施 / 瞬时服务失败；业务 attempt 本身仍合法，不得因一次技术失败自动转成业务终态，不得假设成功，也不得假设失败。 |

TERMINAL ATTEMPT REJECTION 至少覆盖：identity conflict、P1 已绑定其他 Account、candidate Account 已绑定其他 Person、确认者错误或无权、candidate recognition 被明确拒绝、multi-family block、ADULT unsupported、UNKNOWN blocked、invitation terminal（尚未 COMMITTED 的 attempt）、candidate 取消本次 attempt、有权确认者拒绝本次 attempt、并发中失败的 attempt、attempt expiration。具体 enum 名留 Plan。

PENDING 不得用来掩盖 consent invalid / revoked、identity conflict、无权确认者、multi-family block、ADULT、UNKNOWN 或 invitation terminal；这些情形必须判定为 TERMINAL ATTEMPT REJECTION 或 BLOCK，不得等待 consent 自动恢复。

**Operation timeout ≠ attempt expiration（强制）**：

- Operation timeout / transient failure（candidate confirmation request 网络超时、second-party request 瞬时服务错误、unknown operation result 等）：若 binding attempt 本身仍 valid → RETRYABLE OPERATION FAILURE。不得自动终止 attempt、不得擦除已有效 Phase B confirmation、不得假设 operation 失败、不得假设 operation 成功。后续 retry / read-back / idempotent resolution 机制留 Plan。
- Binding attempt expiration（业务 attempt 寿命到期）→ TERMINAL ATTEMPT REJECTION，之后不得 commit。
- 历史 attempt facts：即使 attempt terminal，本合同不要求删除全部 Phase B association / confirmation / audit history；必须没有的是 active authorization、partial Account↔Person binding、ordinary session、active participation。attempt history / confirmations / audit facts 可按合法审计与保留策略留存。

- 未证明为 P1 的 candidate 的 cancel / reject / identity failure / attempt expiration 最多终止该 binding attempt，不得 decline / cancel / expire / withdraw P1 的 invitation。
- invitation lifecycle（含谁有权 cancel / withdraw / decline）由 Slice 4 contract 定义，本合同不新增 invitation authorization。本合同只消费 invitation 有效或已进入 Slice 4 正式定义的 terminal / unusable 状态；可安全引用的终止事件仅限 P1 在合法身份下 decline、server-controlled expiry、Slice 4 已定义的 authorization / validity failure，以及其它仅当 Slice 4 正式批准的终态事件。Slice 4 contract 是 invitation 生命周期的事实源。
- attempt terminal 且 invitation 仍有效：允许在同一有效 invitation 上发起新的 binding attempt（若业务政策允许）。幂等边界是同一 binding attempt（`binding_attempt_id`，语义层）：同一 attempt 的 duplicate / replay 返回同一业务结果；不得声明 `(P1, 微信身份, invitation)` 的永久全局唯一，新 attempt 是新的 attempt identity，不是旧 attempt 的 replay。
- attempt 已在 invitation terminal 前 COMMITTED：binding 保持 COMMITTED；same-attempt replay 返回该历史 COMMITTED 结果，但不得 re-execute commit、不得 revive invitation、不得恢复 participation accept、不得重建 authorization。
- invitation terminal：尚未 COMMITTED 的关联 attempt 均不可再 commit；已 COMMITTED 的 binding 保持 COMMITTED（见上）；未来参与必须新 invitation。
- retry / idempotency / outcome-unknown 的物理表达留 Plan；并发多个 attempt 最终 successful commit 数 ∈ {0, 1}，binding count increase ≤ 1；若全部 attempts 均 recognition failed / consent invalidated / authorization failed / multi-family blocked / gate failed，则 0 commit 是合法结果；其余 terminal rejection。
- attempt 审计只冻结行为：security-relevant outcomes（COMMITTED / PENDING / TERMINAL / RETRYABLE）必须可审计，actor / candidate attribution 在法律与技术允许范围内真实，target / attempt / result 可追溯，不记录 secret、不明文记录微信敏感凭据，不为满足 audit FK 创建 Person / Account，不得削弱 RLS / privacy；storage / event sink / table selection 留 Plan，本合同不要求复用 `business_audit_events`。Case C 在正式 Account 尚不存在即被 Gate 1 阻断时仍必须具备 auditable security outcome。

**年龄与第二方确认主体**

矩阵与产品需求 §19A.2 一致；本节是技术投影，不新增分支。

```text
UNDER_14:
candidate WeChat authentication（独立完成，尚不与 P1 关联）
+ current guardian relationship
+ current valid guardian consent
+ applicable Compliance gates
+ candidate explicit confirmation（针对 P1）
+ current guardian confirmation（target confirmation + candidate recognition）
→ binding may proceed
```


### 12.2A V1 产品 Snapshot 与 CI 差异门禁

> 但不能成为唯一证据链。

### 14.5 Memory Extraction / Rebuild 异步合同

Memory Extraction **不能阻塞用户当前业务提交或当前回复**。

对可能产生长期记忆的正式事件，例如：

- message persisted；
- assessment response committed；
- scene node output committed；
- checkin committed；
- review completed；
- contract / plan version activated；

业务事务在同一个 PostgreSQL transaction 中：

~~~text
保存正式业务事实
+
保存需要的 case_event / business_audit_event
+
通过 pg-boss Drizzle transaction adapter 直接 enqueue job
~~~

异步链路：

~~~text
source business event
→ pg-boss
→ memory_extract route
→ candidate derived memory
→ validate provenance / purpose / visibility
→ derived_memories
→ memory_source_links
→ embedding
~~~

要求：

- job key 至少绑定 source event / source version，重复执行不产生重复 Memory；
- memory_extract 只能基于当前仍有效且当前 Purpose 可用的来源；
- 生成结果先保留来源链接，再允许进入可检索 Memory；
- Memory job 失败、超时或模型不可用，**不能回滚已经成功的 Message / Assessment / Checkin / Review**；
- 失败进入可重试后台状态，不向用户伪装“长期记忆已经更新”；
- Correction / deletion / Consent change / source invalidation 在业务事务中 invalidate，并原子 enqueue memory rebuild job；
- rebuild 必须从当前有效原始/结构化来源重新生成，不能用旧 Derived Memory 作为唯一输入；
- embedding 更新与 Memory 版本绑定，旧 embedding 失效后不得继续被召回。

## 14A. Context Builder 实现合同

Context Builder 是 V1 Agent Runtime 的正式组件，不是“把能找到的数据都塞进 Prompt”。

每次模型调用必须按以下顺序构建：

~~~text
1. actor / family / case / purpose
2. Authorization & Consent 结果
3. current Safety state
4. current Case + phase + current Scene Node
5. current Domain Policy / Scene Package version
6. 当前任务真正需要的结构化事实
7. 当前 Purpose 允许的 Family Memory
8. 必要的 Recent Conversation window
9. 当前适用的 Professional RAG context
10. 当前允许调用的 Tools
11. System / response policy
~~~

### 14A.1 权限边界

Authorization 必须发生在：

- Family Memory 检索前；
- Recent Conversation 取数前；
- Professional RAG 涉及受限内容的检索前；
- Context 组装前。

Context Builder 不接收“整个 Family 对象然后靠 Prompt 隐藏”。

### 14A.2 Source priority

发生冲突时，Context 中的权威顺序是：

~~~text
Current PostgreSQL Domain Facts / current versions
> current Policy / Consent / Safety
> current structured evidence
> derived Family Memory
> recent conversational phrasing
~~~

Derived Memory 不能覆盖当前 Fact / Conflict / UNKNOWN，也不能让已失效历史重新变成当前事实。

### 14A.3 Recent Conversation

Recent Conversation 只用于：

- 保持自然多轮连续性；
- 理解当前指代；
- 避免重复追问。

它不是长期事实源。

窗口大小按 token budget 和任务需要动态取，不要求固定“最近 N 条”；超出预算时优先保留当前任务相关消息和有来源的结构化事实。

### 14A.4 Token budget / trimming

每个 Model Route 定义：

~~~text
max_context_tokens
reserved_output_tokens
memory_budget
rag_budget
recent_conversation_budget
~~~

Context 超预算时按以下顺序处理：

1. 删除重复/低相关最近对话；
2. 缩减低相关 Derived Memory；
3. 缩减低相关 RAG chunk；
4. 保留当前 Case / Scene Node / Policy / Safety / Consent / 关键事实；
5. 仍无法满足则返回 CONTEXT_TOO_LARGE 或要求缩小任务，不允许悄悄丢失安全或业务 Gate。

### 14A.5 ai_run provenance

每次调用至少记录：

~~~text
case_version
context_revision
scene_node_code
purpose
consent_version
policy_version
scene_package_version
memory_ids[]
knowledge_ids[]
recent_message_ids[]
allowed_tools[]
model_route_version
prompt_version
~~~

这样可以回答：

> 这次模型为什么会看到这些内容、又为什么没有看到另外一些内容。

## 15. AI Task Runtime

V1 不建立第二套 AI 工作流状态机。

每次需要 AI 时，由 Application Service 发起一个**明确任务**，例如：

```text
extract_evidence
draft_problem_formulation
explain_formulation
propose_plan
roleplay_child
support_execution_obstacle
review_execution
extract_memory_candidate
risk_review
generate_response
```

AI Task 的输入必须由当前 Domain State + Purpose-bound Context 构造，输出只能是候选结果。

推荐统一合同：

```ts
type AiTaskRequest = {
  runId: string
  taskRole: string
  caseId: string
  actorId: string
  purpose: string
  inputRevision: number
  policyVersion: string
  scenePackageVersion: string
  promptVersion: string
  modelRouteVersion: string
}

type AiTaskResult<T> = {
  runId: string
  candidate: T
  modelId: string
  provider: string
  confidence?: number
  sourceRefs: string[]
  startedAt: string
  completedAt: string
}
```

规则：

- AI Task 不直接 UPDATE Case / Plan / Consent / Safety；
- 正式状态变化只允许通过 Domain Command；
- 每次执行前重新读取当前业务事实；
- 返回时校验 inputRevision / policy / scene package / consent / safety；
- stale 结果只保留为 run evidence，不应用到当前业务；
- 短任务失败可按明确策略重试，但不能重复产生业务副作用。

### 15.1 AI Run 持久化

V1 保存最小 `ai_runs` 记录：

```text
run_id
task_role
case_id
actor_id
purpose
input_revision
model_route_version
prompt_version
policy_version
scene_package_version
status
started_at
completed_at
error_code?
```

业务输入正文不因为可观测需要而复制成第二份长期数据。

### 15.2 Resume / Retry

V1 的 AI Task 默认是可重试的有限任务，而不是跨天挂起的 Agent thread。

需要等待用户、日期或外部事件的长期流程，统一进入：

> PostgreSQL Follow-up Schedule / Domain State

而不是等待 AI runtime 本身。

任何 retry 前必须重新检查：

```text
Case
→ actor/purpose authorization
→ Consent
→ Safety
→ Policy / Scene Package
→ input revision
```

### 15.3 未来复杂工作流边界

如果未来出现真实的跨月、跨系统、复杂补偿式工作流，可以在总体架构定义的 Durable Service Orchestration 边界内评估 Temporal。

该选择不影响 V1 Domain API 和数据模型。

## 18. Response Generation

普通低风险回复：

> 可以流式。

高风险或高影响回复：

> 完整生成并检查后再释放。

### 18.1 API 行为

`POST /cases/:id/messages`

提交后立即返回：

```json
{
  "message_id": "...",
  "run_id": "...",
  "persisted": true,
  "state": "PROCESSING"
}
```

客户端可以：

- 查询 `GET /ai-runs/:id`；
- 在支持时连接受控 response stream；
- 离开后回来继续读取结果。

产品不依赖一个长 HTTP 连接保存业务状态。

### 18.2 用户新输入优先级

已有模型运行时：

> 新消息仍然先保存并进行确定性 Safety 检查。

如果新输入改变：

- risk；
- consent；
- case state；
- plan；
- context revision；

旧 run 标记 STALE 或禁止应用。

### 18.3 Response Release Contract

Decision 校验通过后，Response 仍然是新的模型输出，不能因为 Decision 合法就自动放行。

每个 `ai_run` 在 Response 阶段记录：

```text
release_mode          STREAM_SAFE / BUFFERED_REVIEW / BLOCKED
case_version
context_revision
consent_version
policy_version
package_version
compliance_policy_version
age_band
minor_mode
ai_disclosure_required
generated_content_label_required
allowed_response_intents
allowed_audience
```

#### STREAM_SAFE

只允许：

- 普通共情；
- 已批准知识的低风险解释；
- 当前 Decision 指定的澄清/追问；
- 不改变业务状态的导航信息。

每个可释放单元必须先经过 Compliance Gate，再检查：

- 当前 actor/feature 是否允许；
- 必要 guardian/separate consent 是否有效；
- AI 身份/生成内容标识是否已附加；
- 如适用，连续使用时长提示是否到期；
- intent 仍在白名单；
- 不夹带未允许的行动建议；
- 不把 Hypothesis 表达成 Fact；
- 不泄露 audience 无权获知的来源/内容；
- 不引用当前 RAG allow-set 之外的专业依据。

#### BUFFERED_REVIEW

以下默认完整生成并完成必要检查后再释放：

- 正式方案；
- 实质方案调整；
- 敏感跨成员披露；
- 高影响专业解释；
- 安全/转介内容；
- Domain Policy 指定的其他高影响输出。

#### 流式中断

Stream 每次释放前重新检查：

```text
run status
case/context revision
consent version
policy/package state
safety state
```

发生授权撤回、主线切换、关键纠错、Safety/Compliance 变化或 Package/Policy 停用时：

1. 原 run → `INTERRUPTED` 或 `STALE`；
2. 服务端立即停止发送旧 stream；
3. 客户端收到真实终态；
4. 已经发送的内容不能伪称“已撤回”；
5. 新内容必须基于最新上下文重新运行。

SSE / WebSocket / 轮询最终结果都必须走同一 Release Contract，不能让某个出口绕过校验。

### 18.4 微信小程序 Chunked Streaming Contract

微信小程序不依赖浏览器 `EventSource`。

流式交付采用：

```text
POST /cases/:id/messages
→ message_id + run_id + PROCESSING

GET /api/v1/ai-runs/:id/stream
→ wx.request({ enableChunked: true })
→ RequestTask.onChunkReceived(...)
→ ArrayBuffer
→ incremental UTF-8 decoder
→ frame parser
→ UI incremental render
```

客户端 parser 必须正确处理：

- UTF-8 字符跨 chunk；
- 一个 frame 跨多个 chunk；
- 一个 chunk 含多个 frame；
- stream 中断；
- App 切后台/恢复；
- 网络切换。

`GET /api/v1/ai-runs/:id` 是恢复和最终状态查询兜底。

> **stream 只是交付通道，持久化 ai_run 才是业务真相。**

CloudBase Run / 网关 / CDN 等真实生产链路必须通过 chunk pass-through / buffering readiness test。

不预设 Nginx、关闭 HTTP/2、固定 UI 刷新毫秒数，也不为 AI Streaming 引入 WebSocket。

## 25. pg-boss

pg-boss 负责：

- due follow-up；
- notification dispatch；
- Memory Extraction；
- Memory rebuild；
- async Eval；
- background summary；
- retryable external work。

业务事务不直接依赖：

> 队列任务是否马上执行。

### 25.1 Schedule 与 Job 一致性

方案确认必须在统一 `withRlsTransaction` 内完成：

```text
保存/激活 Plan
+
创建 Follow-up Schedule
+
保存 case_event / business_audit_event
+
pg-boss enqueue（同一 PostgreSQL transaction）
```

Drizzle 使用 pg-boss 官方 transaction adapter（`fromDrizzle(tx, sql)` 或当前稳定等价接口）把当前事务转换成 pg-boss 的 `db` adapter。

禁止：

- 裸传不兼容的 Drizzle transaction object；
- 为同库 pg-boss 再建立 `outbox_events` / Outbox Consumer；
- 在业务事务提交后才“尽力”创建关键 follow-up job。

Job 本身仍必须使用稳定 job key / singleton / idempotency 规则，防止调用方重试产生重复业务副作用。

Job 执行前必须重新检查：

- Case Status；
- schedule_revision；
- Plan Version；
- Consent；
- Notification capability；
- Safety。

旧 Job 即使到期：

> 也不能绕过当前业务事实。

### 25.2 pg-boss Dashboard

V1 使用成熟 **pg-boss Dashboard** 作为内部基础设施运维工具。

负责：

- queue / job / schedule 查看；
- failed / retry / cancel / resume 等运维；
- warning / backlog 排查。

边界：

> **pg-boss Dashboard ≠ 小树荫 Operations Domain UI。**

2. 供应商存在已验证的幂等/查询机制，可确认重试不会制造第二次副作用。

- 供应商可能已经接受但响应丢失；
- 外部请求已发出后 Worker 在本地记账前退出；
- 网络超时且无法确认供应商状态。

`PROVIDER_ACCEPTED` 只表示平台接受请求，不等于 delivery/read/feedback。

**Ordinary login boundary**

## 34. 数据生命周期与删除

### 34.1 数据副本生命周期表

具体 TTL 在上线前根据真实服务目的、法规和供应商条款锁定；没有依据时不能默认永久保存，也不能为了节省资源删除长期事实源。

| 数据类别 | 默认目的 | 日常生命周期规则 | 纠错/撤回 | 主动删除 | 备份恢复 |
|---|---|---|---|---|---|
| 结构化长期档案 / Case / Outcome | 持续家庭服务 | 服务目的仍成立时长期保存；定期核对有效性，不因结案自动清空 | 版本化更正、失效依赖 | 按请求范围清除 | 恢复后先重放删除清单 |
| 原始聊天/证据 | 事实来源与纠错 | 与长期档案分层；具体保留期在上线前由隐私/专业需要确定并版本化 | 更正不覆写历史；用途撤回限制后续使用 | 范围内清除 | 同上 |
| Derived Memory / Embedding | 检索和长期理解 | 仅在有效来源和用途存在时有效；来源失效即失效/重建 | 自动传播 | 清除并重建相关索引 | 不得复活无来源派生内容 |
| AI run 临时上下文 / cache | 当前 AI Task 执行、重试与短期排障 | 最短必要窗口；正式业务事实不放入此层 | stale / consent / safety / revision 变化后禁止复用 | 按 case/person/run 范围清理 | 恢复后不得复活已删除来源或旧上下文 |
| pg-boss job payload | 异步执行 | 完成/取消后按运维审计需要短期保留；payload 最小化 | job 执行前重检 | 取消未来 job并清理相关 payload | 过去提醒不重放 |
| AI 临时上下文/cache | 运行 | 最短必要窗口 | 授权变化立即禁止复用 | 清理 | 不从备份恢复为可用上下文 |
| Phoenix 可识别 Trace / Eval 样本 | 质量 | 默认最小化/脱敏；可识别样本有独立保留策略 | 必要时失效 | 可识别范围清除 | 不作为业务恢复源 |
| 导出文件 | 用户权利交付 | 限时下载，过期自动删除 | 新导出反映当前数据 | 删除 | 不恢复过期导出 |
| 供应商请求副本 | 模型/通知服务 | 以已审核真实条款和配置为准 | 以供应商能力传播 | 记录可执行范围 | 不假定本地恢复可控制供应商副本 |

### 34.2 用户主动删除

按 V1 产品需求：

> 在线数据在核验范围后 7 天内清除。

删除传播显式覆盖：

- raw messages / assertions / observations；
- Case / Plan / Task 等请求范围；
- derived memory / embeddings；
- **AI run 临时上下文 / cache**；
- future schedules；
- pg-boss future jobs / related payload；
- AI cache / temp context；
- exports；
- Phoenix 中可识别样本（若存在）；
- 本项目控制范围内的对象存储副本。

系统维护：

```text
data_requests
+
deletion_replay_ledger
```

`deletion_replay_ledger` 只保存重放删除所需的最小内部标识、请求版本、范围和完成状态，不保存家庭正文。

该 Ledger 必须位于：

> **独立于业务数据库旧恢复点的加密私有持久化位置**

例如受 KMS 保护的私有对象存储追加清单。

删除请求状态：

```text
PENDING
IN_PROGRESS
PARTIAL
FAILED
COMPLETE
```

其中 `COMPLETE` 只能在以下条件**同时满足**时写入：

1. 请求范围内所有**本项目控制的在线副本**均已实际清除或不可逆失效，并取得对应删除证明；
2. 不存在仍待处理的本项目在线副本；
3. 最新 `deletion_replay_ledger` 已可靠写入独立持久化位置。

如果导出文件、AI run 临时上下文、对象存储副本、业务表、派生 Memory/Embedding 等任一应删除在线副本清理失败：

> 请求保持 `PENDING` / `PARTIAL` / `FAILED`，并向用户/运营显示真实待处理范围；不能因为已经写入 Ledger 就标记 `COMPLETE`。

以下与“在线删除完成”分开报告：

- 仍处于 50 天滚动周期内、但已被禁止用于业务恢复的备份副本；
- 项目无法直接控制、只能按已审核供应商条款处理的外部供应商副本。

它们不能用来掩盖本项目在线副本尚未删除。

系统必须能按 `case/person → run_id` 枚举本项目控制的 AI run、临时上下文和 cache；删除时先取消相关运行，再清理对应副本并记录证明。

### 34.3 备份

恢复备份滚动 50 天。

删除在线数据后：

> 备份中的旧副本不用于新业务处理。

恢复时：

> 先从独立 Ledger 取得最新删除清单并重放，再开放服务。

如果无法证明删除清单完整、最新：

> 恢复环境继续隔离。

## 37. 非功能目标与执行预算

### 37.1 事前设计预算

以下是架构约束，不是已经实测的 SLA：

| 路径 | 前台模型调用预算 | 自动重试 | 额外规则 |
|---|---:|---:|---|
| 普通低风险回合 | 最多 2 次：Decision + Response | 整条链最多 1 次可证明安全的瞬时重试 | RAG/Rerank 可用；Memory Extraction 必须后台 |
| 高影响回合 | 最多 3 次：Decision + 必要独立复核 + Response | 同上 | Response 默认 BUFFERED_REVIEW |
| 后台 Extract/Memory/Eval | 不计入前台调用预算 | 由 job policy 单独限制 | 不能阻塞用户消息保存 |
| 未审核跨供应商 fallback | 0 | 0 | 禁止发送真实家庭上下文 |

每个 Model Route 必须配置并强制：

```text
max_foreground_calls
max_retries
per_call_timeout_ms
chain_deadline_ms
max_input_tokens
max_output_tokens
estimated_cost_limit
```

任一层不得在自己内部无限 retry，导致总调用次数跨层放大。

真实试点前必须形成版本化 `pilot_budget_version`，至少包含：

- 月技术预算上限；
- 模型预算上限；
- 单 Case / 单服务轮次可接受的技术成本目标；
- 云、模型、通知、人工四类成本的计量来源；
- 达到预算上限后的降级/停止策略。

金额根据届时真实云规格、模型价格和试点规模批准；缺少真实报价时不伪造固定人民币数字，但 **budget_version 为空时不得开放真实试点**。

### 37.2 用户体验和可靠性目标

| 项 | 设计目标 |
|---|---|
| 普通 API | 不被模型调用阻塞；先以快速持久化并返回真实状态为验收 |
| 用户消息持久化 | API 返回成功前已经写库 |
| 新风险输入 | 不等待已有 AI run；确定性 Safety 抢占普通生成 |
| AI 普通请求 | 有 PROCESSING / SUCCESS / FAILED / STALE / INTERRUPTED |
| 数据权限 | 跨家庭和无授权访问必须失败，属于硬阻断 |
| 身份绑定 | binding attempt 必须返回真实的 COMMITTED / PENDING / TERMINAL ATTEMPT REJECTION / RETRYABLE OPERATION FAILURE；不得部分成功；binding 前不得创建 Person / 普通会话 / active participation；未绑定 candidate 不得通过响应差异探测 P1 门禁 |
| 幂等 | 重试不重复产生业务结果 |
| Follow-up | Worker 重启后业务 Schedule 不丢失 |
| 通知 | UNKNOWN 不盲重试，安静时段和频率策略可验证 |
| 删除 | 能枚举全部副本并证明在线清除/失效传播 |
| Observability | 核心服务不依赖 Phoenix/TCOP APM 可用；AI Trace 与系统监控分离；默认监控不含完整敏感正文 |

具体 p95、并发、RPO/RTO 和人民币单位成本在首次原型压测/成本测量后冻结，并在真实试点前写入 release evidence。

不能把“第一次测到多少”直接当成“目标就是多少”；若实测不能满足体验或预算，必须减少非必要调用/检索步骤、调整模型路由或缩小开放范围。

## 41. 最终实现原则

V1 实现必须始终保持：

```text
V1 产品需求
↓
Common Core + Digital Use Scene Package
↓
Authorization / Consent
↓
Compliance Policy
↓
Domain Policy + Scene Routing
↓
AI Task Runtime
↓
Purpose-bound Context
↓
Professional RAG + Family Domain Memory
↓
TaskModelRegistry
↓
Decision Engine / Generative Model
↓
Schema + Domain + Permission + Safety Validation
↓
Response Release
↓
Domain Command
↓
PostgreSQL
↓
Follow-up Schedule
↓
pg-boss
↓
真实 Notification
↓
真实 Feedback / A5001-A5002 Review / Outcome
```

最重要的边界：

> **V1 产品需求决定产品行为；本文只能实现，不能改写。**

> **PostgreSQL 决定系统业务事实。**

> **Drizzle 是类型安全数据访问层，不是新的业务事实源；RLS 是 `authorize()` 之后的数据库硬防线。**

> **关键 pg-boss Job 与业务写入在同一 PostgreSQL transaction 中原子入队，不经主动 Outbox Consumer。**

> **pg-boss Dashboard 只负责 Queue/Job 基础设施运维，不替代 Refine Operations 的业务运营能力。**

> **Scene Node Manifest / 轻量 deterministic Routing 决定 A1001—A5002 的确定性流程；V1 不引入 XState 作为第二状态源。**

> **Domain Policy 决定专业硬边界和 Intervention 适用性。**

> **Authorization 决定数据边界。**

> **Compliance Policy 决定未成年人/监护人、AI 身份与生成内容标识、拟人化适用性和监管上线门槛；不能由 Prompt 或前端绕过。**

> **AI Task Runtime 只执行明确任务，不拥有 Case 生命周期。**

> **Decision Model 只处理经过定义和评测的有界判断，不自动获得业务写权限。**

> **RAG 解释“为什么/怎么做”，不能代替专业 Gate。**

> **V1 RAG 只在 A(dense+sparse) / B(dense+pg_jieba) / C(dense-only) 三个已定义方案中用 Gold Dataset 选择；pg_textsearch 当前 DEFERRED。**

> **生成模型负责复杂推理和表达，但不拥有事实、Formulation、Consent、Goal、Plan、Contract、Safety 或 Closure 的最终权力。**

> **V1 从第一天正确保存 Outcome 与 provenance，但不提前建设 Similar Case、预测模型、XState runtime、DBOS、Temporal、Langfuse 或 Realtime。**

> **先把 Digital Use 纵向切片完整做对，再用第二 Scene 验证真正的架构复用。**
